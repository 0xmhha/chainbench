# Web UI 작업 규칙

`web/` 의 화면을 만들거나 고칠 때 항상 적용한다. 기능을 넣는 것으로 끝내지 않는다.
누가 어떤 상황에서 이 화면을 쓰는지는 [PRODUCT.md](PRODUCT.md) 가 정본이다.

## 시작 전에

1. `PRODUCT.md` 를 읽고, 이 기능을 쓰는 사람이 주 사용자(실패 원인을 찾는 개발자·QA)인지
   둘째 사용자(상태를 지켜보는 운영자)인지 정한다. 그 사람이 이 화면에서 먼저 봐야 할 것을
   한 문장으로 적는다.
2. 새 화면이나 큰 흐름 변경이면 `/impeccable shape` 로 먼저 설계한다. 작은 수정은 기존
   화면의 흐름과 표현을 따른다.

## 만들 때 기본으로 넣는 것

사용자가 따로 요청하지 않아도 넣는다.

- **데이터**: 상태·진행·metric 은 형태(추세·분포·타임라인·비율)로 먼저 보이게 하고, 원래
  값은 그 옆에서 확인할 수 있게 한다. `<pre>` 덤프나 숫자 나열로 끝내지 않는다. 차트
  형태를 고를 때는 `ui-ux-pro-max` 의 chart 검색을 참고한다.
- **로그와 긴 목록**: 검색, 일치 하이라이트, 레벨·노드 필터, 시점 연계, 많은 양을 다루는
  방법(가상 스크롤 또는 페이지)을 둔다.
- **연결**: 실패·경고가 보이는 곳에서 그 시점의 노드·로그·단계로 바로 건너갈 수 있게 한다.
- **상태**: 빈 상태, 불러오는 중, 오류, 권한 없음, 오래된 데이터를 각각 다르게 보여 준다.
  상태는 색과 글자를 함께 쓴다.
- **조작**: 실행 전에 대상·영향·필요한 권한을 보이고, 되돌릴 수 없는 동작은 그렇다고 적는다.
- **문구**: 한국어가 기본이고 어휘·체인 ID·노드·파일 이름은 엔진 표기를 그대로 쓴다.

## 끝내기 전에

1. 화면을 실제로 띄워(chrome-devtools MCP) 데스크톱 폭과 좁은 폭에서 본다. 긴 데이터, 빈
   데이터, 오류 응답도 확인한다.
2. `/impeccable critique` 로 UX 를, `/impeccable audit` 로 접근성·성능·반응형을 검토하고,
   impeccable detector 를 바뀐 파일에 한 번 돌린다. 지적된 것을 고친 뒤에 끝낸다.
3. `npm --prefix web run build` 로 `internal/dashboard/spa/` 를 다시 만들고 함께 커밋한다.
