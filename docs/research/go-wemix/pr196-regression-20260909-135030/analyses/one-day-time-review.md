# PR196 핵심 33개 예상 시간 검토

**기존 8시간 배정에는 근거가 부족했다. 준비 완료 후에도 담당자 1명이 기본적으로 순서대로 실행·확인하면 약 10~20시간을 계획하는 편이 타당하다.** 8시간 근무일 기준 2~3일 분량이다. 이는 실측값·보장 상한·통계적 신뢰구간이 아닌 계획용 추정이다. 예상 신뢰도는 낮다.

검토 대상은 [핵심 33개 목록](one-day-test-candidates.md), [신규 테스트 원문](additional-tests.md), PR196 보고서의 보존된 JSON이다. 현재 별도 세션의 신규 구현 완료 여부나 하드웨어 성능은 확인하지 않았다. 문서의 미구현·이식 상태를 기준으로 평가했다.

## 추정 전제

- 숙련 담당자 1명, 주 실행 환경 1세트, 기본 직렬 실행 .
- 빌드·이식·신규 테스트 구현·fixture 생성·과거 체인 조사 완료 .
- 작은 폐쇄망 테스트 체인, 로컬 또는 안정적인 내부 연결, 충분한 CPU/메모리/SSD .
- 자동 검증 및 증거 저장 준비, 정상 성공 경로 기준 .
- 문서 원문의 입력 변형·base/head 비교·L2→L3를 생략하지 않음 .

표의 시간은 순수 바이너리 실행 시간만이 아니다. 입력 선택, fixture 복원, 필요한 경로별 reset, 로그·상태 결과 확인을 포함한다. L1/L2 자동 시험이 수초 내 끝나더라도 운영 확인 시간을 별도로 둔 값이다. 최초 공통 환경 기동과 최종 종합 검토는 아래 별도 항목에만 계상했다. N-008의 txpool을 재사용하는 두 RPC 명세에는 추가 관측 시간만 넣었다.

## 합산

| 구분 | 계획 범위 |
|---|---:|
| 기존 18개 실행·확인 | 109~221분 |
| 신규 15개 실행·확인 | 375~735분 |
| 항목별 소계 | 484~956분 (약 8.1~15.9시간) |

테스트 구현·수정, 새 바이너리 빌드, 과거 실제 체인 RLP 조사, 대형 fixture 생성, 전체 메인넷 데이터 동기화, 실패 원인 분석과 패치 작업은 이 범위에 들어 있지 않다. 이 작업이 남아 있으면 별도 일정이 필요하다. 준비 공수가 얼마나 남았는지 확인하지 못했으므로 임의로 몇 시간을 더하는 방식으로 산정하지 않았다.

## 과소 배정된 부분

- 전파·동기화·버전 호환의 기존 150분 배정은 N-004·N-005·N-006·N-013·N-014와 정상 full/downloader/fetcher/snap를 모두 담는다. 항목별 추정 합계만 253~520분이다. 가장 큰 부족분이다.
- N-007은 단일 장애 시험이 아니다. 정상·종료·TTL과 prefetch 양쪽을 다뤄야 한다. TTL이 실제로 얼마인지와 복구 허용 시간을 고정하기 전에는 30~60분도 확정할 수 없다.
- N-004의 과거 블록 조사와 정책 결정, N-013의 합법 로그 workload 준비는 실행 시간과 분리해야 한다. 준비가 안 된 상태에서 시험을 시작하면 조사·개발 작업으로 바뀐다.
- 33개는 상위 항목 수다. N-006만 size gate에서 3버전 × 3경계를 갖고 실제 peer 확인을 추가한다. 각 항목을 한 번의 짧은 RPC 호출로 계산할 수 없다.

## 원본에서 확인한 대기 조건

- [wemix-chain-up 원본](../sources/chainbench/tests/tc/go-wemix/chain-up/01-wemix-chain-up.json)은 블록 2까지 최대 180초 기다린다. 환경 생성·RPC 준비·검증 전체가 180초 안에 끝난다는 뜻은 아니다.
- [wemix-node-crash 원본](../sources/chainbench/tests/tc/go-wemix/fault/01-wemix-node-crash.json)은 블록 3까지 최대 300초, 다른 노드의 blockAdvance는 최대 180초 기다린 뒤 restartNode를 호출한다. 두 timeout의 합 8분은 정상 소요 시간도 전체 시험 상한도 아니다.
- 같은 장애 JSON에는 restart 후 동기화 완료를 확인하는 별도 assertion이 없다. 원본 실행을 재기동 후 상태 수렴 검증의 대체 증거로 쓰지 않는다. 선정한 N-007·N-014의 복구 관측과 구분한다.
- [Brioche RPC 원본](../sources/chainbench/tests/tc/go-wemix/rpc/01-wemix-brioche-block-reward.json)은 블록 2를 기다린 뒤 지정 높이 5와 15의 보상을 조회한다. 실제 블록 15 도달까지 대기하거나 정확한 반감률을 검증하는 시험이 아니다.
- full/snap 체인 크기, snapshot/DB 크기, CPU·메모리·디스크, 블록 간격, token TTL, 실행별 환경 재사용 정책과 측정 로그는 고정되지 않았다. 따라서 상세한 초 단위 실행 시간이나 완료 확률을 제시할 근거는 없다.

## 하루 완료 가능성을 판정하는 방법

현재 근거로는 33개를 하루 완료 대상으로 확정하지 않는다. **2~3일을 확보하고, 사전 측정 결과가 나오는 경우에만 하루로 압축**한다. 준비된 환경에서 N-004·N-005·N-007·N-013·N-014부터 각각 한 차례 실행해 실제 동기화·reset·TTL·로그 검토 시간을 기록한다. 이후 나머지 항목을 합산한다. 이 준비 실행의 시간도 작업 공수에서 누락하지 않는다.

독립 환경과 자동화된 판정이 있으면 L1/L2 경계 시험과 L3 동기화 시험을 겹칠 수 있다. 다만 두 환경이 같은 CPU·디스크를 경쟁하거나 담당자가 결과를 순차 확인하면 절반으로 줄지 않는다. 현재는 병렬 실행 수와 인력이 정해지지 않아 병렬 완료 시간을 확정하지 않는다.

실측 후 `환경 기동 + 의존관계를 반영한 가장 긴 실행 경로 + 최종 대조 + 재실행 여유`가 480분 이하인지 확인한다. 같은 환경을 수정하는 장애·pool·생산자 전환 시험은 동시에 두지 않는다. 전체 명세의 입력을 생략하지 않고 이 조건을 만족할 때만 하루 계획으로 확정한다.

이번 검토에서는 선정 33개와 우선순위를 유지했다. 테스트 실행·코드 수정은 하지 않았다. 시간 추정치와 계산은 [JSON](one-day-time-review.json)에 보존했다.
