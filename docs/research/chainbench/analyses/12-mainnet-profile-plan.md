## 1. HANDOFF가 바꾼 것

HANDOFF는 사용자 요구사항 9개를 정본으로 기록하고, 검토 방식에 제약을 걸었다.
그중 이 작업에 직접 닿는 것은 여덟 개다.

### 1차 검토를 철회하는 부분

**철회 1 — `internal/app/composition` 신설을 앞세우지 않는다.**
1차 검토의 S2는 PR #419의 P1을 근거로 새 패키지를 만들고 `compose.go`의 변환을
그리로 옮기자고 했다. HANDOFF는 두 문장으로 이를 막는다. "원래의 P0–P5 계획은
잠정적이다", 그리고 "앞선 다이어그램이 제안했다는 이유만으로 기존 경계를 새
추상으로 대체하지 말라". 다음 어시스턴트에게 주는 시작 메시지에도 "기본적으로
옛 P0–P5 계획을 구현하지 말라"고 적혀 있다.

개정: 주입 지점은 새 패키지가 아니라 **기존 호출 지점**에 둔다. `app.RunSuite`,
`app.AttachRun`, `testengine.AttachWorkspaceRun` 세 곳이 이미 세 실행 경로의
입구다. 프로필을 여기서 만들어 넘긴다. 패키지 분리는 그 자체의 근거가 생긴
뒤에 별도로 판단한다.

**철회 2 — consolidation-plan §0-2 개정 권고를 거둔다.**
1차 검토는 §0-2("testengine → chainsetup 의존은 구조의 일부")와 PR #419의 F1이
충돌하니 PR #419를 따르고 §0-2를 고치자고 했다. 지금은 근거가 약하다. F1은
문서상의 제안이고, HANDOFF는 그 제안을 잠정으로 격하했다. 정본을 잠정 문서에
맞춰 고치는 것은 순서가 거꾸로다.

개정: §0-2는 그대로 둔다. 충돌은 **열린 결정**으로 기록하고(§6-2), 이 작업은
어느 쪽에서도 성립하도록 설계한다. 프로필을 testengine 바깥에서 만들어 넣으면
testengine이 chainsetup을 부르든 말든 주입은 성립한다.

### 플랜을 강화하는 부분

**요구사항 5는 이 작업의 정본이다.** "기존 RPC URL로, 체인을 구성하지 않고,
가용한 능력이 지원하는 테스트를 돌릴 수 있어야 한다." 1차 검토에서 내가
추론으로 넣었던 "능력에 따른 SKIP"이 사용자 요구사항으로 확정됐다. 순서를
앞당긴다.

**요구사항 4는 프로필의 내용물을 규정한다.** "선언과, 미리 준비된 바이너리·
자격증명·서버 목록 사이의 경계를 분명히 하라." 즉 프로필에 자격증명을 담으면
안 된다. 문서는 셋으로 갈린다(§4-1).

**요구사항 2는 프로필에 원격을 넣게 한다.** 격리망의 여러 서버에 노드를 배치하고
그 환경에 테스트를 돌려야 한다. "SSH를 지원한다는 것만으로 폐쇄망 준비가
증명되지 않는다." 프로필은 원격 엔드포인트를 표현해야 하고, 공개 다운로드 없이
자산이 있어야 한다.

**요구사항 8은 프로필의 확장자를 지금 정하게 한다.** `.json` → `.dsl` 이동이
논의 중이고 "env 파일 접미사"도 그 논의에 포함된다. 프로필은 세 번째 문서
종류다. 따로 정하면 논의가 두 번 열린다.

**요구사항 9는 데몬 의존을 막는다.** `chainbenchd`는 없다. 현재 세 번째 바이너리는
`chainbench-dashboard`다(확인함: `cmd/` 아래 `chainbench`, `chainbench-dashboard`,
`chainbench-mcp`). 주입은 CLI만으로 성립해야 한다.

**요구사항 6은 MCP 표면을 뒤에 붙인다.** LLM이 MCP로 체인을 구성하고 선택적으로
테스트를 돌린다. 프로필도 MCP에서 지정할 수 있어야 한다. 다만 합의된 순서는
CLI → MCP → 대시보드·데몬이므로 뒤 단계다.

**`chain up`의 완료 계약이 열려 있다.** HANDOFF가 "지금 가장 시급한 논의"로
꼽은 질문이다. 성공한 `chain up`이 보장하는 것은 배포된 입력인가, 띄운
프로세스인가, RPC 응답인가, 관측된 블록 진행인가. 이 답이 없으면 compose 경로의
프로필 도출이 언제 유효한지 말할 수 없다(§6-1).

**Stablenet 실패는 열린 채로 둔다.** 기준선 `20260913T101856Z`에서 Stablenet은
FAIL이다. 이후의 통과가 원인을 밝힌 것이 아니다. 케이스를 기계로 치환하는
단계에서 이 FAIL이 PASS로 바뀌면 그것은 진전이 아니라 신호 손실이다.

## 2. 확인한 코드 사실

HANDOFF의 서술 중 이 작업에 걸리는 것을 직접 확인했다. 아래는 소스를 읽어
확인한 것이며, 실제 체인을 띄워 본 결과가 아니다.

- 단계는 둘뿐이다. `UpDeploy`("deploy")와 `UpStart`("start")이고 비우면
  `UpStart`다(`internal/chainsetup/verbs_up.go:24-29,141-149`). "RPC 준비됨"이나
  "블록 진행 관측됨"은 단계가 아니다. `--stage=start`는 바이너리를 요구하고,
  원격 대상이면 그 경로는 원격 호스트의 경로다.
- 세 번째 바이너리는 `chainbench-dashboard`다. `chainbenchd`는 없다.
- env 참조 방식은 이미 있다. 케이스 옆의 `<id>.env.json` 또는 위쪽 `env/`
  디렉터리를 8단계까지 올라가며 찾는다(`internal/dsl/files.go:18,34,48-49`).
  그런데 `tests/tc` 아래 `.env.json` 파일은 **0건**이고, `"env": {` 인라인
  선언은 **205건**이다. 참조 기계는 있는데 쓰이지 않는다.
- 값 보간 문법도 이미 있다. `${name}` 형태이고 `tests/tc`의 118개 파일이 쓴다
  (`internal/dsl/interp/binding.go:23`). 다만 값의 출처는 실행 중 `read` 결과뿐이다.
- 주소 리터럴은 40자리 기준 138개 파일에 있다. 시스템 컨트랙트
  `0x...1000`~`0x...1004`는 62개 파일, `gasTip` 읽기는 14개 파일이다.
- 원격 자격증명은 이미 환경변수로 들어온다. `CHAINBENCH_REMOTE_HOST`,
  `..._USER`, `..._PASS`, `..._KEY_FILE`, `..._KEY_PASSPHRASE`,
  `..._PORT`. E2E는 `WEMIX_BIN`, `WBFT_BIN`, `GSTABLE_BIN`을 쓴다.
  요구사항 4가 말하는 "미리 준비된 것"의 경계가 여기에 이미 그어져 있다.
- attach는 `accounts.ForChain(chain)`으로 서명 프로토콜만 고른다
  (`internal/testengine/attach.go:156`). 계정 값은 오지 않는다.
- `nodegate`의 `WantChainID`가 0이면 체인 ID 불일치를 검사하지 않는다
  (`internal/testengine/nodegate.go:44-56`).

## 3. 이 작업이 검토 단위 어디에 놓이는가

HANDOFF는 다음 검토 단위를 다섯 개로 잡았다. 이 작업은 새 트랙이 아니라 그중
3번과 4번이다.

| HANDOFF 단위 | 이 작업과의 관계 |
|---|---|
| 1. 로컬 CI 구성 전용 → 점검 → 이후 attach 테스트 → 명시적 정리 | compose 경로 프로필 도출이 여기 걸린다 |
| 2. 격리망 다중 서버 구성 | 원격 엔드포인트·자산 가용성이 프로필에 들어온다 |
| **3. DSL 구성·테스트와 `.dsl` 발견·이행** | **프로필 문서 종류와 확장자를 여기서 정한다** |
| **4. 기존 RPC 테스트 적격성과 저장된 환경·실행 관계** | **작업 목적 그 자체다** |
| 5. CLI 리팩토링 통합 후 MCP 노출 | 프로필의 MCP 표면이 여기다 |

따라서 결과 보고도 단위마다 끊어서 낸다. 한 번에 전체 설계를 확정해 제출하지
않는다. HANDOFF가 명시적으로 막은 방식이다.

## 4. 개정된 설계

### 4-1. 문서는 셋으로 갈린다

요구사항 4가 요구하는 경계다.

**선언(git에 있고 값이 없다).** 케이스와 `env`. 노드를 몇 대 띄우는지, 어떤
능력과 어떤 값을 필요로 하는지를 쓴다. 주소도 수수료도 쓰지 않는다.

**프로필(git에 있고 값이 있으나 비밀은 없다).** 대상 망 하나를 가리킨다.
엔드포인트, 컨트랙트 주소, 체인 ID, 계정 **참조**, 테스트 상수, 제공 능력.

**미리 준비된 것(git에 없다).** 바이너리, 개인키, 서버 목록, 접속 자격증명.
이미 환경변수와 keyring으로 들어오고 있다. 프로필은 이것을 **이름으로 참조만**
한다. 프로필에 개인키를 쓰면 요구사항 4를 어기고 보안 규칙도 어긴다.

프로필 모양(초안, 확장자는 §6-3에서 결정):

```json
{
  "schemaVersion": "2", "kind": "profile", "id": "stablenet-local",
  "chain": "stablenet", "chainId": 0,
  "endpoints": [
    {"name": "bp1", "role": "bp", "rpc": "", "ws": "", "metrics": ""}
  ],
  "accounts": {
    "faucet": {"keyRef": "keyring:stablenet-faucet"},
    "alice":  {"fund": "1000000000000000000"}
  },
  "contracts": {"registry": "0x...1000", "govStaking": "0x...1001"},
  "params": {"feeTip": "", "blockTimeout": "180s"},
  "provides": ["rpc", "consensus", "process-control", "metrics"]
}
```

`provides`가 요구사항 5의 핵심이다. 케이스는 `needs`로 필요한 능력과 키를
선언하고, 프로필이 못 주면 그 케이스는 SKIP이며 사유가 남는다. 맨 RPC로 붙으면
`process-control`도 `metrics`도 없으므로 fault 케이스는 자동으로 빠진다.
HANDOFF가 "RPC URL만으로 프로세스 제어·키·메트릭 의존 테스트를 약속하지 말라"고
한 것을 기계로 지키는 방법이다.

### 4-2. 세 경로가 같은 프로필을 만든다

```
chain up --stage=start → workspace.json + 매니페스트 + genesis → 프로필(도출)
run --attach --workspace-dir  → 같은 도출 + 기록된 역할
run --rpc <url>               → 프로필 파일(사용자 제공), 없으면 엔드포인트만 있는 최소 프로필
```

compose 경로의 도출은 `--stage=deploy`에서는 성립하지 않는다. 노드가 떠 있지
않기 때문이다. 이 경계는 §6-1의 답에 달려 있다.

식별자는 새로 만들지 않는다. HANDOFF가 "구성 ID는 이미 있고 워크스페이스 위치에서
파생된다"고 기록했다. 프로필은 그 ID를 참조한다.

### 4-3. 모듈별 역할

새 패키지를 만들지 않는다(§1 철회 1).

- `internal/dsl` — `ProfileV2` 타입, 스키마, 케이스의 `needs`, 파일 발견.
  문법만 소유한다.
- `internal/testengine` — 실행 입력에 프로필을 받는다. `interp.Bindings`의
  초기값으로 넣는다. `needs`와 `provides`를 맞춰 SKIP 사유를 낸다.
  `nodegate.WantChainID`를 프로필 값으로 채운다.
- `internal/app` — 세 경로의 입구에서 프로필을 만들어 넘긴다. 변환 코드가
  커지면 그때 분리를 따로 판단한다.
- `internal/chains/*` — 패밀리 기본값(시스템 컨트랙트 주소, 수수료 읽는 방식,
  합의 네임스페이스)과 실제 RPC로 능력을 확인하는 어댑터.
- `internal/testhelper` — faucet·deploy·load의 로컬 서명 전환, 수수료 출처 교체,
  `expect: reject`의 사유별 판정.
- `internal/arch` — `tests/tc`의 주소 리터럴을 금지하는 테스트. 완료 조건 2번의
  기계 판정이다.
- `cmd/chainbench` — `--profile` 플래그. MCP 표면은 단위 5에서.

## 5. 개정된 순서

단계를 HANDOFF의 검토 단위에 맞춰 다시 끊었다. 각 단위가 끝날 때 결과와 미결
결정을 내고 사용자의 방향 수정을 받는다.

| 순서 | 검토 단위 | 내용 | 증명하는 완료 조건 |
|---|---|---|---|
| A | 단위 4 (선) | 능력 기반 적격성만 먼저. 케이스 `needs`, 프로필 `provides`, SKIP 사유 코드 | 없음(요구사항 5) |
| B | 단위 3 | 프로필 문서 종류 확정. 확장자·발견 규칙을 `.dsl` 논의 안에서 결정 | 1번 |
| C | 단위 4 | 세 경로가 프로필을 만들어 testengine에 넘긴다. chainId를 프로필 값과 비교 | 3번 |
| D | 단위 1·2 | 매니페스트 기본값, 실제 능력 확인, 원격 엔드포인트 | 4번의 절반 |
| E | — | testhelper 로컬 서명·수수료·reject 판정 | 3번을 실제 망에서 성립 |
| F | — | 케이스 치환(시스템 컨트랙트 62건 → gasTip 14건 → 나머지), arch 테스트 0건 | 2번 |
| G | 단위 5 | 한 스위트를 여러 프로필로 실행, 결과에 프로필 ID, MCP 표면 | 4번 |

A를 맨 앞에 둔 것이 1차 검토와 다르다. 요구사항 5가 정본이 됐고, A는 프로필
파일 없이도 시작할 수 있다. 케이스의 `needs`만 붙이면 된다.

F를 돌릴 때마다 기준선 `20260913T101856Z`와 대조한다. **Stablenet의 FAIL은 FAIL로
남아야 한다.** 치환 때문에 그 케이스가 SKIP이나 PASS로 바뀌면 치환을 되돌린다.

## 6. 열린 결정

### 6-1. `chain up` 성공이 보장하는 것 (HANDOFF의 최우선 질문)

배포된 입력인가, 띄운 프로세스인가, RPC 응답인가, 블록 진행인가. 지금 코드에는
`deploy`와 `start` 두 단계뿐이고 그 위의 관측은 단계가 아니다. 이 답이 compose
경로 프로필이 언제 유효한지를 정한다. 사용자와 먼저 논의할 항목이고, 기존
bootstrap·health 경로를 읽은 뒤에 정해야 한다.

### 6-2. §0-2 와 PR #419 F1 의 충돌

consolidation-plan §0-2는 testengine → chainsetup 의존을 구조의 일부로 확정했고,
PR #419의 F1은 같은 의존을 문제로 본다. **이번 작업에서는 결정하지 않는다.**
프로필을 바깥에서 넣으면 어느 쪽이든 성립한다. 기록만 남긴다.

### 6-3. 프로필의 확장자와 발견 규칙

요구사항 8의 `.dsl` 논의 안에서 함께 정한다. 재료는 있다. `.env.json` 참조
기계가 이미 있고 8단계까지 위로 찾는데, 실제 사용은 0건이다. 쓰이지 않는 이유를
먼저 보는 편이 새 규칙을 만드는 것보다 낫다.

### 6-4. E 단계(로컬 서명 전환)를 이 작업에 넣는가

넣지 않으면 실제 메인넷에서 faucet·deploy·load가 돌지 않는다. 넣으면 범위가
커진다. 지금 로컬 서명 sendTx는 gas 21000 고정이고 컨트랙트 생성을 못 한다.

### 6-5. "메인넷"이 인스턴스인가 패밀리인가

같은 패밀리의 새 망은 프로필만 더하면 된다. 새 합의 엔진은 매니페스트와 어댑터가
필요하다. 완료 조건 4번이 어느 쪽을 뜻하는지 문안에 적어야 한다.

## 7. 단점과 위험

- **문서 종류가 셋이 된다.** 케이스, env, 프로필. 요구사항 4가 요구한 경계이지만
  사용자가 어디에 무엇을 쓰는지 헷갈릴 수 있다. 문서 첫 줄에 셋의 차이를 적어야
  한다.
- **A 단계가 SKIP을 늘린다.** 능력 기반 적격성을 켜면 지금 통과하던 케이스 일부가
  SKIP으로 바뀔 수 있다. 기준선의 SKIP 27건과 비교해 증가분을 사유별로 설명해야
  한다. HANDOFF의 원칙대로 SKIP은 PASS가 아니다.
- **compose 경로 도출이 체인마다 다르다.** genesis에 시스템 컨트랙트가 없는
  체인은 매니페스트 기본값에 기댄다. wbft 매니페스트의 바이너리 이름 불일치도
  이때 같이 걸린다.
- **격리망에서 확인하지 못한 것이 남는다.** 원격 엔드포인트를 프로필에 넣어도
  폐쇄망에서 자산이 실제로 있는지는 별개다. HANDOFF가 짚은 그대로다.
- **이 문서의 근거는 소스 읽기다.** 체인을 띄워 확인한 것이 아니다. 위 수치는
  grep 결과이고, 파일별 치환 난이도는 보지 않았다.
