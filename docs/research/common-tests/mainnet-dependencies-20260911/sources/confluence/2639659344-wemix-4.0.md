### NODE-001 — 하드포크 블록 전후 동작 비교

**목적**: Croissant 블록 이전(wpoa)과 이후(WBFT)의 블록 헤더 구조가 올바르게 전환되는지 확인

**사전 조건**: `CroissantBlock = 100` 설정, go-wemix 블록 0\~99 데이터 준비

**입력값**: 블록 99 (wpoa), 블록 100 (WBFT)

**실행 절차**:

1. go-wemix로 블록 0\~99 생성
2. go-wbft 노드로 해당 체인 동기화
3. 블록 100에서 WBFT 합의 엔진 전환 확인
4. 블록 99와 100의 Extra 데이터 구조 비교

**기대 결과**:

- 블록 99: wpoa 형식 Extra 필드
- 블록 100: WBFTExtra 형식 (`RandaoReveal`, `CommittedSeal` 포함)

**검증 포인트**:

- `istanbul_getWbftExtraInfo(100)` 정상 반환 (EpochInfo 포함)
- 블록 99에서 해당 API 호출 시 오류 또는 wpoa 형식 반환

### NODE-002 — go-wemix 데이터로 go-wbft 기동 및 블록 검증

**목적**: go-wemix가 생성한 wpoa 블록 데이터(chaindata)를 그대로 사용해 go-wbft 노드가 정상 기동되고, 기존 블록을 올바르게 읽고 검증하는지 확인

**사전 조건**: go-wemix 노드가 블록 0 \~ CroissantBlock-1 까지 생성한 뒤 종료된 상태, 동일 `chainId`, 동일 `CroissantBlock` 설정 포함 genesis config

**입력값**: go-wemix의 기존 `--datadir` 경로

**실행 절차**:

1. go-wemix 노드 종료
2. go-wbft 바이너리로 교체 후 **동일 **`--datadir` 지정해서 기동
3. go-wbft가 기존 chaindata를 정상 인식하는지 로그 확인
4. `eth_blockNumber` 가 go-wemix 종료 시점 높이와 일치하는지 확인
5. 기존 wpoa 블록의 상태 루트 조회 (`eth_getBlockByNumber(N).stateRoot`) 정상 반환 확인
6. wpoa 블록 내 트랜잭션 조회 — `eth_getTransactionByHash`, `eth_getTransactionReceipt` 정상 반환 확인
7. 이후 블록 동기화 정상 동작 확인 — CroissantBlock 도달 후 `eth_blockNumber` 단조 증가 확인

**기대 결과**: go-wbft가 go-wemix chaindata를 오류 없이 읽고, 블록 및 트랜잭션 조회가 정상 동작하며 기존 블록 높이부터 계속 운영 가능

**검증 포인트**:

- 기동 시 DB 호환 오류 없음
- `eth_blockNumber` = go-wemix 마지막 블록 높이
- `eth_getBlockByNumber(N).stateRoot` 정상 반환 (wpoa 블록 기준)
- `eth_getTransactionReceipt(txHash)` 정상 반환 (wpoa 구간 tx)
- `CroissantBlock` 도달 후 WBFTExtra 형식 전환 확인
- `CroissantBlock` 이후 `eth_blockNumber` 계속 증가 (블록 생성 유지)

### NODE-003 — Full Sync 동기화

**목적**: Full Sync 모드에서 신규 노드가 기존 네트워크에 조인하여 Croissant 하드포크 구간을 포함한 체인을 정상 동기화하는지 확인

**사전 조건**: 체인 높이 200 이상인 기존 노드. 하드포크 전(go-wemix, wpoa, 블록 0\~99)과 후(go-wbft, WBFT, 블록 100\~)에 각각 아래 tx 포함: 자산전송 Legacy tx 1건, 자산전송 DynamicFee tx 1건, 자산전송 FeeDelegation tx 1건, DynamicFee로 컨트랙트 배포 tx 1건, DynamicFee로 컨트랙트 상태 변경 tx 1건. 신규 노드 준비 (`--syncmode full`), bootnodes 설정

**입력값**: `--syncmode full`

**실행 절차**:

1. 신규 노드 Full Sync 모드로 기동 (bootnodes 설정 포함)
2. 피어 연결 및 블록 0부터 순차 동기화 진행 확인
3. Croissant 블록 경계 통과 확인
4. 동기화 완료 후 기존 노드와 블록 해시 및 상태 루트 비교

**기대 결과**: 신규 노드가 모든 블록 검증하며 동기화 완료, 상태 루트 일치

**검증 포인트**:

- `net_peerCount` ≥ 1 (피어 연결)
- `eth_getBlockByNumber(latest).stateRoot` 기존 노드와 일치
- `eth_getBlockByNumber(CroissantBlock).hash` 기존 노드와 동일

**회귀 테스트 참조**: RT-A-1-02

> RT-A-1-02 변경내역: 차이: go-stablenet RT는 Authorized 계정·GasTip 강제 적용 등 Anzeon 기능 검증을 포함하지만 go-wbft에는 해당 기능이 없어 제외. go-wbft는 하드포크 전(go-wemix wpoa 블록 0\~99)·후(go-wbft WBFT 블록 100\~) 각 타입별 tx(자산전송 Legacy·DynamicFee·FeeDelegation 각 1건, 컨트랙트 배포·상태변경 각 1건)가 포함된 200블록+ 체인 필요.

### NODE-004 — Snap Sync 동기화

**목적**: Snap Sync 모드에서 신규 노드가 기존 네트워크에 조인하여 Croissant 하드포크 구간을 포함한 체인을 정상 동기화하는지 확인

**사전 조건**: 체인 높이 200 이상인 기존 노드 (snap pivot이 CroissantBlock 이후에 형성되도록 ≥200 블록 필요). 하드포크 전(go-wemix, wpoa, 블록 0\~99)과 후(go-wbft, WBFT, 블록 100\~)에 각각 아래 tx 포함: 자산전송 Legacy tx 1건, 자산전송 DynamicFee tx 1건, 자산전송 FeeDelegation tx 1건, DynamicFee로 컨트랙트 배포 tx 1건, DynamicFee로 컨트랙트 상태 변경 tx 1건. 신규 노드 준비 (`--syncmode snap`), bootnodes 설정

**입력값**: `--syncmode snap`

**실행 절차**:

1. 신규 노드 Snap Sync 모드로 기동 (bootnodes 설정 포함)
2. 피어 연결 및 스냅 피벗 선정 확인
3. state 동기화 완료 후 기존 노드와 상태 루트 비교

**기대 결과**: 신규 노드가 스냅 피벗 이후 state 동기화 완료, 상태 루트 일치

**검증 포인트**:

- `net_peerCount` ≥ 1 (피어 연결)
- `eth_getBlockByNumber(latest).stateRoot` 기존 노드와 일치
- 피벗 이후 `eth_getBalance` 조회 가능

**회귀 테스트 참조**: RT-A-1-03

> RT-A-1-03 변경내역: 차이: snap pivot이 Croissant 이후에 형성되도록 200블록+ 및 하드포크 전후 tx 포함 필요. RT는 128블록 이상만 요구.

### NODE-005 — 노드 재기동 후 블록 생산 재개 및 체인 정합성

**목적**: 밸리데이터 노드를 종료(강제 또는 정상)한 뒤 재기동했을 때, 체인 정합성이 유지되고 1초 블록 주기가 회복되며 재기동 노드가 블록 서명에 참여하는지 확인

**사전 조건**: 밸리데이터 4개 이상 구성, Croissant 블록 이후 운영 중, `BlockPeriodSeconds=1` 설정

**입력값**: 밸리데이터 1개 종료 (강제: `kill -9` 또는 정상: SIGTERM)

**실행 절차**:

1. 밸리데이터 1개를 블록 N 생산 직후 종료 (`kill -9` 또는 SIGTERM)
2. 나머지 노드에서 블록 생성 계속됨 확인
3. 종료된 노드 동일 `--datadir`로 재기동
4. 재기동 노드가 최신 블록까지 동기화 완료 확인
5. `eth_getBlockByNumber("latest", false)` 폴링으로 연속 블록 5개 수집 후 timestamp 간격 확인
6. `istanbul_getCommitSignersFromBlock(M)` 으로 재기동 노드의 서명 참여 확인

**기대 결과**: 쿼럼(2/3+) 유지로 합의 중단 없음, 재기동 후 1초 블록 주기 회복, 재기동 노드가 합의에 재참여

**검증 포인트**:

- 장애 중 나머지 노드에서 블록 생성 계속됨
- 재기동 후 `eth_blockNumber` 동기화 확인
- 블록 해시 불일치 없음
- 재기동 후 연속 5개 블록의 `timestamp` 차이가 모두 1초
- `istanbul_getCommitSignersFromBlock(M)` 결과에 재기동 노드의 coinbase 주소 포함

**회귀 테스트 참조**: RT-A-1-04

> RT-A-1-04 변경내역: 차이: RT는 1초 블록 주기 회복과 seal 정보로 BP 참여 여부를 검증하며, go-wbft는 여기에 더해 `istanbul_getCommitSignersFromBlock(M)`으로 재기동 노드의 coinbase 주소가 Commit 서명자 목록에 포함되는지 추가 확인.

### NODE-006 — NCP 주소 공백 포함 파싱 검증

**목적**: genesis config의 NCP 주소 목록에 공백이 포함된 경우에도 올바르게 파싱되어 GovNCP 컨트랙트에 정상 등록되고 노드가 기동되는지 확인

**사전 조건**: `UseNCP = true`, 공백 포함 NCP 주소로 기동된 노드, `NCP_1_ADDR` 환경 변수 설정

**실행 절차**:

1. `GovNCP.ncpCount()` 조회 → `> 0` 확인 (NCP 등록 여부)
2. `GovNCP.isNCP(NCP_1_ADDR)` → `true` 확인 (공백 trim 후 정상 등록)
3. `blockNumber > 0` 확인 (노드 정상 기동 상태)

**기대 결과**: 공백이 trim되어 NCP 주소가 정상 등록, 노드 기동 오류 없음

**검증 포인트**:

- `ncpCount() > 0`
- `isNCP(NCP_1_ADDR) == true`
- `blockNumber > 0` (노드 정상 기동)

## 2. 트랜잭션 처리 / 가스 정책

### TX-001 — 일반 트랜잭션 생성 / 전파 / 포함 / 확정

**목적**: Croissant 하드포크 이후 일반 ETH 전송 트랜잭션이 정상적으로 처리되는지 확인

**사전 조건**: WBFT 네트워크 운영 중 (Croissant 이후), 잔액 있는 계정

**입력값**: `from`: 잔액 보유 계정, `to`: 임의 계정, `value`: 1 WMX, `gasLimit`: 21000

**실행 절차**:

1. `eth_sendRawTransaction`으로 트랜잭션 제출
2. `eth_getTransactionByHash`로 txpool 포함 확인
3. 다음 블록에서 트랜잭션 포함 확인
4. `eth_getTransactionReceipt`로 확정 확인

**기대 결과**: `status: 1` (성공), 수신자 잔액 증가

**검증 포인트**:

- `receipt.status == 1`
- `receipt.blockNumber > 0`
- `eth_getBalance(to)` 증가 확인

**회귀 테스트 참조**: RT-A-2-01, RT-A-2-02

> RT-A-2-01/02 변경내역: 차이: go-stablenet RT-A-2-02는 Authorized 계정(tx.GasTipCap 기반)과 일반 계정(header.GasTip 강제 적용) 두 경로로 effectiveGasPrice를 검증하지만, go-wbft에는 GasTip governance·Authorized 계정이 없으므로 effectiveGasPrice = baseFee + min(tipCap, gasFeeCap-baseFee) 단일 경로만 검증.

### TX-002 — BaseFee 미달 트랜잭션 거부

**목적**: `maxFeePerGas < BaseFee`인 트랜잭션이 txpool에서 거부되는지 확인

**사전 조건**: Croissant 이후 블록, `eth_getBlockByNumber("latest").baseFeePerGas`로 현재 BaseFee 확인

**입력값**: `maxFeePerGas = BaseFee - 1` 로 설정한 트랜잭션

**실행 절차**:

1. `eth_getBlockByNumber("latest").baseFeePerGas` 로 현재 BaseFee 조회
2. `maxFeePerGas = BaseFee - 1` 로 트랜잭션 전송
3. 거부 오류 메시지 확인

**기대 결과**: txpool 진입 거부, 블록에 미포함

**검증 포인트**:

- `eth_sendRawTransaction` 응답에 오류 반환
- `eth_getTransactionByHash` 조회 불가

**회귀 테스트 참조**: RT-A-2-05b

> RT-A-2-05b 변경내역: 차이: Anzeon 없음. go-wbft에서는 maxFeePerGas \< baseFee 조건으로 거부.

### TX-003 — DynamicFee Tx (type 0x2) 정상 처리

**목적**: EIP-1559 DynamicFee 트랜잭션(type 0x2)이 정상 처리되고 `effectiveGasPrice`가 올바르게 계산되는지 확인

**사전 조건**: Croissant 이후 블록, `eth_getBlockByNumber("latest").baseFeePerGas`로 현재 BaseFee 확인

**입력값**: `type: 0x2`, `maxFeePerGas = BaseFee + tip`, `maxPriorityFeePerGas = tip`

**실행 절차**:

1. `eth_getBlockByNumber("latest").baseFeePerGas` 로 현재 BaseFee 조회
2. `type: 0x2`, `maxFeePerGas >= BaseFee` 로 트랜잭션 전송
3. 블록 포함 후 receipt 확인
4. `effectiveGasPrice = baseFee + min(tip, maxFeePerGas - baseFee)` 계산 검증

**기대 결과**: 트랜잭션 정상 처리, type 0x2, effectiveGasPrice 올바르게 계산

**검증 포인트**:

- `receipt.status == 1`
- `receipt.type == 0x2`
- `receipt.effectiveGasPrice == baseFee + min(tipCap, gasFeeCap - baseFee)`

**회귀 테스트 참조**: RT-A-2-02

> RT-A-2-02 변경내역: 차이: go-stablenet RT는 Authorized/일반 계정 이중 경로로 effectiveGasPrice를 검증하지만, go-wbft에는 GasTip governance·Authorized 계정이 없으므로 effectiveGasPrice = baseFee + min(tipCap, gasFeeCap-baseFee) 단일 경로만 검증.

### TX-004 — 수수료 위임 (Fee Delegation) 트랜잭션

**목적**: WEMIX 고유 Fee Delegation 트랜잭션 (FeePayer 필드 포함)이 Croissant 이후에도 정상 처리되는지 확인

**사전 조건**: Sender 계정, FeePayer 계정 (충분한 잔액), Croissant 이후 블록

**입력값**: Sender 서명 + FeePayer 서명이 모두 포함된 트랜잭션

**실행 절차**:

1. Sender가 트랜잭션 서명
2. FeePayer 서명 추가
3. `eth_sendRawTransaction`으로 제출
4. receipt 및 잔액 변화 확인

**기대 결과**:

- 트랜잭션 정상 처리
- 가스비가 Sender가 아닌 FeePayer에서 차감

**검증 포인트**:

### TX-010 — Nonce 순서 보장

- blockNumber(N) ≤ blockNumber(N+1) ≤ blockNumber(N+2)
- 같은 블록이면 transactionIndex(N) \< transactionIndex(N+1) \< transactionIndex(N+2)

### TX-013 — 트랜잭션 교체 (queued tx replacement)

**목적**: queued 상태의 tx(nonce gap으로 대기 중)와 동일 nonce로 더 높은 `gasFeeCap`의 tx를 재발행 시 기존 tx가 교체되는지 확인

**사전 조건**: 계정의 현재 nonce가 N인 상태에서 nonce N+2로 tx 전송 (nonce N+1 미전송으로 queued 상태)

1. tx 1 전송 (nonce N+2, gasFeeCap = X) — nonce gap으로 queued 상태

3. tx 2 전송 (nonce N+2, gasFeeCap = X × 1.1 이상)

**기대 결과**: queued tx가 동일 nonce 높은 gasFeeCap tx로 교체, tx 1은 txpool에서 제거

**검증 포인트**:

- `txpool_content.queued` 에서 tx 2만 존재 (tx 1 제거)
- 블록에 tx 2만 포함
- tx 1 hash: `eth_getTransactionByHash` null 반환

**회귀 테스트 참조**: RT-A-2-09

> RT-A-2-09 변경내역: 차이: pending tx가 아닌 queued tx(nonce gap으로 대기 중) 교체를 테스트. RT는 pending tx 교체.

### WBFT-003 — View Change 발생 및 라운드 체인지 후 블록 연결 검증

**목적**: Proposer 노드 무응답 시 View Change가 발생하여 합의가 재개되고, 라운드 체인지 이후 블록이 `parentHash`로 올바르게 연결되는지 확인

**사전 조건**: 밸리데이터 4개 이상, `RequestTimeoutSeconds` 설정 확인

**입력값**: Proposer 역할의 노드 종료 (네트워크 차단 효과)

**실행 절차**:

1. 현재 Proposer 노드 종료
2. `RequestTimeoutSeconds` 경과 후 RoundChange 메시지 전파 확인
3. 다음 라운드에서 새 Proposer 선정 및 블록 생성 확인
4. `istanbul_getWbftExtraInfo(N).PrevRound > 0` 확인
5. 원래 Proposer 노드 재기동
6. 이후 연속 5블록의 `parentHash` 체인 연결 검증

**기대 결과**: RoundChange 후 새 라운드에서 블록 정상 생성, 라운드 체인지 이후 블록도 `parentHash` 연결 유지

**검증 포인트**:

- `istanbul_getWbftExtraInfo(N).PrevRound > 0` (라운드 전환 흔적)
- `block[N].parentHash == block[N-1].hash` (연속 5블록 검증)
- 블록 생성 간격이 `RequestTimeoutSeconds`만큼 길어지지만 결국 생성됨

**회귀 테스트 참조**: RT-B-09 (View Change), RT-B-10 (블록 연결, WBFT-004 통합)

### WBFT-010 — RandaoReveal / MixDigest 검증

**목적**: 각 블록의 `RandaoReveal`이 Proposer의 ECDSA 서명이고, `MixDigest = XOR(이전 MixDigest, RandaoReveal)` 규칙이 연속 블록에서 올바르게 유지되는지 확인

3. `eth_getBlockByNumber(N+1).mixHash == XOR(block[N].mixHash, block[N+1].RandaoReveal)` 검증

**검증 포인트**:

- `block[N+1].mixHash == XOR(block[N].mixHash, block[N+1].RandaoReveal)`
- `RandaoReveal` 서명 복구 주소 = `block[N+1].miner`

### WBFT-011 — 쿼럼 계산 검증 — validator 3개 (전원 필요)

**목적**: BFT 공식 `F = floor((n-1)/3)` 에 따라 n=3일 때 F=0, QuorumSize=3 (전원 필요)임을 검증. n=3에서 2명만으로 합의되면 안 됨

**사전 조건**: 밸리데이터 3개 구성 (`n=3`)

**입력값**: 밸리데이터 3개 중 1개 종료

**실행 절차**:

1. `istanbul_getValidators` 로 밸리데이터 수 = 3 확인
2. `QuorumSize() == 3` 확인 (F=0이므로 전원 필요)
3. 밸리데이터 1개 종료
4. 나머지 2개 노드에서 블록 생성 시도 → 중단 확인
5. 종료된 노드 재기동 후 합의 재개 확인

**기대 결과**: n=3에서 1개 장애 시 쿼럼 미달(2 \< 3)로 블록 생성 중단, 재기동 후 재개

**검증 포인트**:

- `istanbul_getCommitSignersFromBlock(N)` 에서 3개 서명자 확인 (정상 동작 시)
- 1개 장애 중 `eth_blockNumber` 증가 없음
- `QuorumSize = n - floor((n-1)/3) = 3 - 0 = 3` 임을 `istanbul_status` 로 간접 확인

**기대 결과**: 긴급 모드 활성 중 GovStaking 작업 전체 차단, NCP 투표는 영향 없음

**검증 포인트**:

- `emergencyMode() == true`
- stake/unstake/delegate 모두 `"operation not permitted by council"` revert
- `vote()` 정상 동작 확인

**기대 결과**: 긴급 모드 해제 후 GovStaking 작업 정상 재개

**검증 포인트**:

### GOV-019 — Staker INACTIVE → ACTIVE 재활성화

**목적**: 전액 언스테이킹으로 INACTIVE 상태가 된 Staker가 `stake(minimumStaking 이상)` 호출로 ACTIVE 재활성화되는지 확인

**사전 조건**: GOV-004 통과 (INACTIVE 상태 Staker 존재)

**입력값**: `stake(minimumStaking)` — `msg.value = minimumStaking`

**실행 절차**:

1. INACTIVE Staker 확인 (`isStaker(staker) == false`)
2. Operator가 `GovStaking.stake(minimumStaking)` 전송 (payable)
3. `isStaker(staker) == true` 확인 (ACTIVE 전환)
4. `GovStaking.stakers()` 목록에 포함됐는지 확인
5. 다음 에폭에서 Validator 후보로 복귀 확인

**기대 결과**: `stake()` 금액 ≥ minimumStaking 시 INACTIVE → ACTIVE 전환, Validator 후보 복귀

**검증 포인트**:

- 재활성화 후 `isStaker(staker) == true`
- `Staked(staker, amount)` 이벤트
- `stakers()` 목록 포함 확인
- 재활성화 금액 \< minimumStaking 시 여전히 INACTIVE (revert 없이 단순 stake만 추가)

### GOV-020 — 수수료율 변경 — 위임자 없음 (즉시 적용)

**사전 조건**: GOV-003 통과, 해당 Staker에 위임자 없음

**입력값**: `requestChangingFee(newFeeRate)`

**실행 절차**:

2. 동일 트랜잭션에서 `ChangingFeeRateExecuted(staker, newFeeRate)` 이벤트 확인 (즉시 적용)
3. `stakerInfo(staker).feeRate == newFeeRate` 확인

**기대 결과**: 위임자 없으면 `requestChangingFee()` 단일 호출로 즉시 변경

**검증 포인트**:

### GOV-021 — 수수료율 변경 — 위임자 있음 (지연 적용)

**목적**: 위임자가 있는 Staker의 수수료율 변경 시 `changeFeeDelay` 경과 후에만 `executeChangingFee()` 로 적용 가능한지 확인

**사전 조건**: GOV-011 통과 (위임자 있는 Staker 상태), `changeFeeDelay = 604,800초` (GovConfig)

**입력값**: `requestChangingFee(newFeeRate)`, `executeChangingFee(staker)`

**실행 절차**:

1. Operator가 `requestChangingFee(newFeeRate)` 전송
2. `ChangingFeeRateRequested(staker, oldFeeRate, newFeeRate)` 이벤트 확인
3. `changeFeeDelay` 경과 전 `executeChangingFee(staker)` → revert 확인
4. `changeFeeDelay` 경과 후 `executeChangingFee(staker)` → 성공 확인
5. `stakerInfo(staker).feeRate == newFeeRate` 확인

**기대 결과**: 위임자 있으면 지연 후에만 적용, 지연 전 실행 시 revert

**검증 포인트**:

- `ChangingFeeRateRequested` 이벤트 발생
- 지연 전 `executeChangingFee` 실패: `"the request cannot be executed before delay time"`
- 지연 후 `ChangingFeeRateExecuted(staker, newFeeRate)` 이벤트

### GOV-022 — Claim 권한 — 타 Staker 보상 탈취 불가

**목적**: `claim()`은 누구나 호출 가능하지만, Operator가 타 Staker를 대상으로 호출할 때 해당 Staker의 보상이 Operator에게 지급되지 않아야 함. 또한 위임·스테이킹 관계가 없는 계정은 `"no reward to claim"` 으로 거부됨을 확인

**사전 조건**: Staker A (Operator A), Staker B (Operator B) 각각 등록 완료, 두 Staker 모두 블록 리워드 누적, 제3자 계정 C (Staker A에 위임 없음)

**입력값**: Operator A가 `claim(stakerB, false)` 호출, 계정 C가 `claim(stakerA, false)` 호출

**실행 절차**:

1. Operator A로 `GovStaking.claim(stakerB, false)` 전송
2. Staker B의 rewardee 잔액이 Operator A에게 지급되지 않음 확인 (Operator B 잔액 변화 없음)
3. 계정 C (위임 없음)가 `claim(stakerA, false)` 전송
4. `"no reward to claim"` 오류로 실패 확인

**기대 결과**: Operator A → `claim(stakerB)`: Staker B 보상이 Operator A에게 전달되지 않음 / 계정 C → `claim(stakerA)`: `"no reward to claim"` 오류

**검증 포인트**:

- Operator A의 `claim(stakerB)` 호출 후 Operator A 잔액 증가 없음
- Staker B의 rewardee 잔액 변화 없음
- 계정 C의 `claim(stakerA)`: `receipt.status == 0`, `"no reward to claim"`

### GOV-023 — Credential 만료 기간 개별 검증

**목적**: `withdraw(N)` 이 미만료 credential을 건너뛰고(skip) 만료된 credential만 선택적으로 처리하는지 확인. unbondingPeriodStaker(긴 기간)보다 unbondingPeriodDelegator(짧은 기간)이 먼저 만료되는 상황에서, staker credential이 미만료인 채로 delegator credential만 출금 가능함을 검증

**사전 조건**: OP\_A(VAL\_A의 operator)가 VAL\_B에 위임한 상태. unbonding 기간은 체인 파라미터에서 블록 기반으로 동적 조회

**입력값**: OP\_A가 `unstake()` → `undelegate(VAL_B)` 순서로 호출하여 동일 sender의 credential\[N\](staker, 긴 unbonding), credential\[N+1\](delegator, 짧은 unbonding) 생성

**실행 절차**:  
**Setup**

1. OP\_A가 `GovStaking.delegate(VAL_B, amount)` → VAL\_B에 위임 (delegator credential 생성 준비)

**Credential 생성**  
2. OP\_A가 `GovStaking.unstake(amount)` → credential\[N\] 생성 (만료: unstake\_block + unbondingPeriodStaker)  
3. OP\_A가 `GovStaking.undelegate(VAL_B, amount)` → credential\[N+1\] 생성 (만료: undelegate\_block + unbondingPeriodDelegator)

**delegator unbonding 만료 후 (credential\[N+1\] 만료, credential\[N\] 미만료)**  
4. `withdraw(1)` 호출 → 미만료 credential[N](staker) skip, 만료된 credential[N+1](delegator) 처리 → 성공 확인

- `Withdrawn` 이벤트 확인 (withdrawalIndex = N+1)

**staker unbonding 만료 후 (credential\[N\] 만료)**  
5. `withdraw(1)` 호출 → credential[N](staker) 처리 → 성공 확인

- `Withdrawn` 이벤트 확인 (withdrawalIndex = N)

**기대 결과**: `withdraw(N)` 은 미만료 credential을 건너뛰며 만료된 credential에 대해서만 순서에 관계없이 출금 처리. `withdrawalIndex`는 "가장 오래된 still-live 슬롯"을 가리키도록 업데이트됨

**검증 포인트**:

- delegator unbonding 만료 시점: `withdraw(1)` → 성공, credential[N+1](delegator) 금액 환급, credential[N](staker) skip
- `Withdrawn` 이벤트 존재 확인 (credential\[N+1\] 처리)
- staker unbonding 만료 시점: `withdraw(1)` → 성공, credential[N](staker) 금액 환급
- `Withdrawn` 이벤트 존재 확인 (credential\[N\] 처리, 모든 credential 처리 완료)

### RPC-018 — txpool\_status / txpool\_content

**목적**: `txpool_status`와 `txpool_content`가 pending/queued tx 상태를 정확하게 반환하는지 확인

**사전 조건**: EN 노드 피어 연결 가능, ACCOUNT\_A 계정 잔액 있음

**입력값**: `txpool_status`, `txpool_content`

**실행 절차**:

1. EN 노드(`en_2`) 피어 연결 해제 (격리 — 채굴 차단)
2. nonce N tx 전송 → pending (격리 중 채굴 안 됨)
3. nonce N+2 tx 전송 (nonce gap) → queued
4. `txpool_status` 호출 → pending/queued 수 확인
5. `txpool_content` 호출 → 상세 내용 확인
6. 피어 재연결

**기대 결과**: `pending ≥ 1, queued ≥ 1`, content에서 각 tx 상세 정보 반환

**검증 포인트**:

- `txpool_status.pending ≥ 1`, `txpool_status.queued ≥ 1`
- `txpool_content.pending`에 nonce N tx 포함
- `txpool_content.queued`에 nonce N+2 tx 포함

**회귀 테스트 참조**: RT-G-4-02, RT-G-4-03
