## 1. etcd & Work/Token

### ETCD-01 — Work Key 삭제 시 자동 복구

- **목적**: etcd `work` 키 삭제 후 `syncCheck`가 과반 합의 헤드로 자동 재구성하여 채굴을 복구하는지 확인
- **사전 조건**: BP 멤버 ≥3인 정상 운영 etcd 클러스터, 노드 간 정상 동기화 상태, admin/debug RPC 접근 가능
- **입력값**: `work` 키(삭제 대상)
- **실행 절차**:
    1. `admin.etcdGetWork()` 또는 `debug.etcdGet("work")`로 현재 값 기록
    2. `eth_blockNumber`로 현재 높이 확인
    3. `admin.etcdDeleteWork()` 호출로 `work` 키 삭제
    4. 최대 30초 대기하며 `eth_blockNumber` 진행 및 `debug.etcdGet("work")` 재생성 관측
- **기대 결과**: 삭제 직후 신규 블록 생산 일시 중단, 30초 이내 `syncCheck`가 과반 합의 헤드(`states/2+1`)로 `work` 재구성 후 생산 재개
- **검증 포인트**:
    - `debug.etcdGet("work")`가 재생성되며 값이 클러스터 최신 헤드와 일치
    - 재개된 블록 높이가 삭제 시점 이상으로 진행
    - 로그 `sync check: found consensus block, setting work`

### ETCD-02 — Work Key 오염(손상/미래) 덮어쓰기 복구

- **목적**: `work` 키에 손상 JSON 또는 미래 높이 주입 시 `syncCheck`가 과반 합의 헤드로 덮어써 복구하는지 확인
- **사전 조건**: BP 멤버 ≥3인 정상 운영 etcd 클러스터, 노드 간 정상 동기화 상태, admin/debug RPC 접근 가능
- **입력값**: (a) Unmarshal이 실패하는 JSON 문자열, (b) 로컬 head보다 앞선 미래 높이 + 임의 해시 JSON
- **실행 절차**:
    1. `debug.etcdGet("work")`로 정상 값 백업
    2. `debug.etcdPut("work", "<Unmarshal 실패 JSON 문자열>")` 주입 후 관측
    3. 정상 복구 확인 후 `debug.etcdPut("work", "{height: 현재+1000, hash: 0x...}")` (어떤 peer도 보유하지 않는 미래값) 주입 후 관측
    4. 각 케이스에서 30초 내 `work` 재구성 및 블록 생산 확인
- **기대 결과**: Unmarshal 실패 JSON은 무시 후 consensus 재구성; 미래 높이(peer echo 부재)는 consensus 재구성으로 덮어쓰기. 두 경우 모두 정상 헤드 복구
- **검증 포인트**:
    - 로그 `sync check: ignoring invalid work`(Unmarshal 실패), `work-key not echoed by any peer, rebuilding via consensus`(미래값)
    - `debug.etcdGet("work")`가 클러스터 합의 헤드로 갱신
    - 블록 생산 지속

### ETCD-03 — Work Key Behind 오염 시 체인 정지 및 Rewind 거부

- **목적**: `work` 키에 과거 높이 주입 시 노드가 역행을 거부하고 정지하며, 수동 삭제로 복구되는지 확인
- **사전 조건**: BP 멤버 ≥3인 정상 운영 etcd 클러스터, 노드 간 정상 동기화 상태, admin/debug RPC 접근 가능
- **입력값**: 로컬 head보다 낮은 과거 높이 + 해당 높이의 실제 해시 JSON
- **실행 절차**:
    1. `eth_blockNumber`로 현재 head 확인
    2. `debug.etcdPut("work", "{height: head-10, hash: <과거 실제 해시>}")` 주입
    3. 30초 이상 대기하며 생산 정지 및 로그 관측
    4. `admin.etcdDeleteWork()` 수동 삭제
    5. 30초 내 복구·재개 관측
- **기대 결과**: 과거 `work` 주입 시 rewind 거부 및 생산 정지(setHead 역행 없음), 수동 삭제 후 consensus 재구성으로 30초 내 복구
- **검증 포인트**:
    - 로그 `sync check: ahead of work, aborting`
    - 오염 `work`가 남아 있는 동안 블록 생성 중단(`eth_blockNumber` 정지)
    - 삭제 후 생산 재개

### ETCD-04 — 손상 Token Key 30초 syncCheck 복구

- **목적**: Unmarshal이 실패하는 `token` 주입 시 `syncCheck`가 자동 삭제/리셋하여 채굴 정상화하는지 확인
- **사전 조건**: BP 멤버 ≥3인 정상 운영 etcd 클러스터, 노드 간 정상 동기화 상태, admin/debug RPC 접근 가능
- **입력값**: Unmarshal이 실패하는 `token` 문자열(예: 중괄호 누락 등)
- **실행 절차**:
    1. `debug.etcdGet("token")`로 정상 값 백업
    2. `debug.etcdPut("token", "<Unmarshal 실패 JSON 문자열>")` 주입
    3. 30초 대기하며 `token` 삭제/리셋 및 블록 생산 관측
- **기대 결과**: Unmarshal 실패 `token`은 `syncCheck`가 `etcdDelete`로 제거, 다음 토큰 획득으로 채굴 정상화
- **검증 포인트**:
    - `debug.etcdGet("token")`가 삭제 또는 정상 값 리셋
    - 30초 내 블록 생산 지속

### ETCD-05 — 만료 TTL Token Key 즉시 복구

- **목적**: 과거 TTL(`Till < now`) 유효 JSON `token` 주입 시 다음 마이너의 토큰 획득 단계에서 즉시 삭제/재획득하는지 확인
- **사전 조건**: BP 멤버 ≥3인 정상 운영 etcd 클러스터, 노드 간 정상 동기화 상태, admin/debug RPC 접근 가능
- **입력값**: (a) `Till`이 미래(예: `now+60초`)인 유효 JSON `token`, (b) `Till < now`인 만료 JSON `token`
- **실행 절차** (전체를 30초 이내에 완료해 `syncCheck` 미개입 보장):
    1. `debug.etcdGet("token")` 백업, `eth_blockNumber`로 현재 head 기록
    2. 대상 BP 노드 `miner.stop`(해당 노드가 유효 토큰을 쥔 채 정지한 상황 재현)
    3. 정지된 노드의 유효 토큰(a) 주입 → 모든 노드의 acquire가 `ErrExists`로 차단되어 생산 정지 유도
    4. 5초 내 `eth_blockNumber` 동결(정지) 확인
    5. 만료 토큰(b)으로 덮어쓰기
    6. (b) 저장 시점부터 다음 블록 생성까지 경과 시간 측정
- **기대 결과**: 유효 토큰 동안 생산 정지, 만료 토큰 저장 후 다음 토큰 획득 시도에서 `syncCheck`(30초) 대기 없이 재개
- **검증 포인트**:
    - 유효 토큰 주입 중 `eth_blockNumber` 동결
    - 만료 토큰 저장 \~ 재개까지 소요 시간이 `syncCheck`(30초) 임계값 이하
    - `debug.etcdGet("token")`의 `Till`이 미래로 갱신(재획득 완료)

## 2. 블록 생산, 타임스탬프 보정 및 합의 규칙

### MINING-01 — 생산자 타임스탬프 단조 증가

- **목적**: 생성 블록 타임스탬프가 직전 블록 이상으로 단조 증가하는지 확인(생산자 floor = `parent.Time`)
- **사전 조건**: 정상 운영 체인
- **입력값**: 연속 블록 범위 `[N, N+k]`
- **실행 절차**:
    1. 연속 블록 범위 `eth_getBlockByNumber(n).timestamp` 수집
    2. 각 `n`에 대해 `timestamp[n] >= timestamp[n-1]` 확인
- **기대 결과**: 모든 연속 쌍에서 타임스탬프 단조 증가(동률 허용)
- **검증 포인트**:
    - 위반 쌍 0건
    - 생산자측 보장이며 import 검증 규칙은 아님(정상 운영 관측 한정)

### MINING-02 — 노드 재개 시 Time-It Fast Catch-up

- **목적**: 정지 후 재개 시 `timeIt behind` 감지로 최단 시간(`BlockMinBuildTime`) 속성 채굴 후 설정 `blockInterval`로 복귀하는지 확인
- **사전 조건**: 다중 BP 노드, 대상 노드에 miner RPC 접근
- **입력값**: 정지 시간(블록 간격의 수 배 이내, `2×height×blockInterval` 미만)
- **실행 절차**:
    1. 대상 노드 `miner.stop()` 또는 프로세스 SIGSTOP
    2. 클러스터가 수 블록 진행하도록 대기
    3. `miner.start()`/SIGCONT 또는 노드 재기동
    4. 재개 직후 생성 블록 간격 및 이후 수렴 관측
- **기대 결과**: behind 구간에서 `BlockMinBuildTime`(≈300ms) 간격 속성 채굴로 따라잡은 뒤 설정 `blockInterval`로 복귀
- **검증 포인트**:
    - 재개 직후 블록 간격이 일시적으로 매우 짧음(속성 채굴)
    - 이후 `blockInterval`로 수렴
    - 과도하게 뒤처진 경우(간격의 2배 초과)엔 미트리거 — 정지 시간 조절 필요

### MINING-03 — Miner Limit 중복 채굴 금지

- **목적**: BP 멤버 N≥3일 때 동일 노드가 최근 `N/2` 블록 윈도우 내 재채굴하지 않는지 확인
- **사전 조건**: BP 멤버 N≥3, Pangyo 이후 높이
- **입력값**: 연속 블록 범위
- **실행 절차**:
    1. 연속 블록 범위 `eth_getBlockByNumber(n).miner` 수집
    2. 각 생산자에 대해 직전 `N/2` 블록 내 중복 여부 계산
    3. (선택) 거버넌스로 멤버 2로 축소 후 동일 관측
- **기대 결과**: N≥3 구간에서 어떤 노드도 `N/2` 윈도우 내 재채굴 없음; 멤버 ≤2 구간은 제한 미적용
- **검증 포인트**:
    - `N/2` 윈도우 위반 0건
    - 멤버 ≤2에서는 제한 해제 확인

## 3. Brioche 하드포크 및 반감기 보상

### BRIOCHE-01 — Brioche API 스케줄 조회

- **목적**: Brioche 설정·회차별 스케줄 정보가 API로 정상 조회되는지 확인
- **사전 조건**: Brioche config 설정된 체인(메인넷 활성)
- **입력값**: 없음
- **실행 절차**:
    1. `wemix.briocheConfig` 호출
    2. `wemix.halvingSchedule` 호출
- **기대 결과**: `briocheConfig`가 반감기 설정값, `halvingSchedule`이 회차별 스케줄 반환
- **검증 포인트**:
    - `HalvingRate == 50`
    - 회차별 경계 높이 연속성·일관성
    - Brioche 미설정 시 `halvingSchedule` nil

### BRIOCHE-02 — 높이별 Brioche 블록 보상 쿼리

- **목적**: 임의 높이 보상 쿼리 시 50% 감축 및 완료 후 0원 반환 정확성 확인
- **사전 조건**: BRIOCHE-01과 동일
- **입력값**: 반감기 전 / 반감기 후 / 완료(`FinishRewardBlock` 이후) 높이
- **실행 절차**:
    1. `wemix.getBriocheBlockReward(FirstHalvingBlock-1)` 조회
    2. `wemix.getBriocheBlockReward(FirstHalvingBlock)` 조회
    3. `wemix.getBriocheBlockReward(FinishRewardBlock+1)` 조회
- **기대 결과**: 반감기마다 정확히 절반(`×0.5^times`), `FinishRewardBlock` 이후 0
- **검증 포인트**:
    - 반감 경계 전후 값 비율 = 0.5
    - 완료 높이 이후 == 0
    - 미래 높이 쿼리로 검증 가능, 온체인 실측은 높이 도달 필요

### BRIOCHE-03 — Brioche 반감기 실제 보상 감축·배분

- **목적**: 반감기 높이 도달 시 거버넌스 보상액을 무시하고 50% 감축된 보상이 수혜 계정에 비율대로 배분되는지 확인
- **사전 조건**: 첫 반감기 블록(`FirstHalvingBlock`) 도달 필요
- **입력값**: 반감기 경계 전후 블록
- **실행 절차**:
    1. 경계 전후 블록의 수혜 계정(Staking/Ecosystem/Maintenance/FeeCollector) `eth_getBalance` 델타 측정
    2. `wemix.getBriocheBlockReward(n)`로 기대 총보상 산출
    3. 블록 헤더 `rewards` 필드와 대조
- **기대 결과**: 경계 이후 블록 총보상 절반 감축, 거버넌스 blockReward 무시(Brioche 스케줄 적용), 배분 비율은 거버넌스 설정 유지
- **검증 포인트**:
    - 수령자 잔액 델타 합 == `getBriocheBlockReward(n)`
    - 거버넌스 blockReward 변경이 총보상에 미반영(Brioche 우선)

## 4. 온체인 거버넌스-노드 런타임 동적 연동

### GOV-01 — 거버넌스 멤버 add/remove 시 BP·피어 동적 갱신

- **목적**: 멤버 추가/제거로 `modifiedBlock` 변경 시 노드가 BP 목록·피어를 갱신하는지 확인
- **사전 조건**: 거버넌스 add/removeMember 가능
- **입력값**: 추가/제거 대상 멤버 노드 정보
- **실행 절차**:
    1. `admin.wemixInfo`의 `nodes`·`modifiedblock` 기록
    2. 거버넌스 add/removeMember 제안·투표·finalize
    3. finalize 이후 `admin.wemixInfo` 재조회 및 `admin.miners()` 확인
- **기대 결과**: `modifiedblock`이 finalize 블록으로 갱신, `nodes` 목록 반영, 신규 BP는 `addPeer`로 자동 추가, 이후 생산자 집합 변화
- **검증 포인트**:
    - `modifiedblock` bump
    - `nodes` 목록 add/remove 반영
    - 신규 피어 연결(`admin.miners()`/`admin.peers`)

## 5. WEMIX 3.0 API

### RPC-01 — WEMIX 통합 상태 조회 (`admin.wemixInfo`)

- **목적**: `admin.wemixInfo`가 최신 거버넌스/etcd/레지스트리 통합 상태를 정상 반환하는지 확인
- **사전 조건**: BP 노드에서 admin RPC 접근
- **입력값**: 없음
- **실행 절차**:
    1. `admin.wemixInfo` 호출
- **기대 결과**: 거버넌스/etcd/레지스트리/스테이킹 통합 상태 및 런타임 파라미터 반환
- **검증 포인트**:
    - 필수 필드 존재 및 유효값
    - etcd 리더 정보 포함
    - `modifiedblock`이 최신 거버넌스 변경 높이 반영

### RPC-02 — WEMIX 커스텀 헤더 필드 조회

- **목적**: `eth_getBlockByNumber` 응답에 `rewards`/`fees`/`minerNodeSig`/`baseFeePerGas`가 포함되는지 확인
- **사전 조건**: PoA 블록(London 이후)
- **입력값**: 임의 블록 높이
- **실행 절차**:
    1. `eth_getBlockByNumber(n, false)` 호출
    2. 응답 JSON 필드 확인
- **기대 결과**: `rewards`/`fees`/`minerNodeSig` 노출, `baseFeePerGas`는 London 이후 블록에서 노출
- **검증 포인트**:
    - 4개 필드 존재
    - `minerNodeSig` 값 유효(비어있지 않음)
    - `baseFeePerGas`는 `head.BaseFee != nil`일 때만 노출
