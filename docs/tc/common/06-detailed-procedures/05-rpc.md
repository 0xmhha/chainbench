## CT-RPC-001 · 최신 블록 번호 조회

- **목적**: 블록 번호가 계속 늘어나는지 확인한다.
- **의존 요소**: RPC 주소·API 노출
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 일정 간격으로 블록 번호를 여러 번 조회한다.
- **기대 결과**: 모든 노드의 번호가 기다린 높이 이상이고, 이전 값 이상으로 늘어난다. 기본 RPC 가 빈 값이 아닌 답을 준다.
- **자동 테스트**: 2026-09-30에 basic-rpc-health 와 remote-rpc-health 를 하나로 합쳤다. 둘은 체인 차이가 아니라 원본 테스트 둘이었고, remote 판은 이름과 달리 스스로 망을 세워 한 노드만 봤다. 노드마다 "0 이상" 을 보던 것은 2026-09-29에 고쳤다. 블록 번호는 음수가 될 수 없어 그 단언은 노드가 무엇을 답해도 통과했고, 창세 블록에 멈춘 노드도 초록불이었다. 높이 2를 기다린 뒤이므로 따라오고 있는 노드는 모두 2 이상이어야 하고, 멈춘 노드는 여기서 걸린다. 그다음 실제로 더 올라가는지 본다. 마지막 둘은 remote 판에서 옮겨 온 것으로, `web3_clientVersion` 과 `net_peerCount` 가 빈 값이 아닌지 본다. 살아 있다는 말이 블록 번호 하나로만 성립하지 않게 한다.
- **비고**: 기존 명세: RT-A-4-01, RPC-001 / 자동 테스트: basic-rpc-health (PR196-TC-007) / PR196 우선순위: P1/P2 / 2026-09-30에 remote-rpc-health(PR196-TC-028)를 합쳐, 한 파일로 세 체인을 돈다.

## CT-RPC-002 · 블록 번호로 블록 조회

- **목적**: 최신 블록을 번호로 조회하면 필수 필드가 있는지 확인한다.
- **의존 요소**: RPC 주소·API 노출
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 최신 블록을 조회한다.
    2. 번호, 해시, 트랜잭션 목록 필드를 확인한다.
- **기대 결과**: 번호와 해시가 16진수이고 트랜잭션 목록 필드가 있다.
- **체인별 차이**: WEMIX4.0 명세는 합의 정보 포함까지 요구한다. 그 부분은 2체인이라 제외했다.
- **비고**: 기존 명세: RT-G-1-01, RPC-002 (부분 대응) / 자동 테스트: block-transactions-field / PR196 우선순위: P1

## CT-RPC-007 · 잔액 조회

- **목적**: 잔액이 있는 계정의 잔액이 정확히 조회되는지 확인한다.
- **의존 요소**: 테스트 계정, RPC 주소·API 노출
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 알려진 계정의 잔액을 조회한다.
    2. 송금 전후로 다시 조회한다.
- **기대 결과**: 0보다 크고 송금 후 변화가 반영된다. 돌아오는 값이 16진 수량 형식이다.
- **자동 테스트**: 2026-09-30에 genesis-balance 와 remote-balance-check 를 하나로 합쳤다. 둘은 체인 차이가 아니라 원본 테스트 둘이었고 단계가 열세 개까지 같았다. remote 판에만 있던 0 주소 잔액의 16진 형식 확인 한 줄을 남겼다. 남은 id 를 genesis-balance 로 한 것은 remote 판이 이름과 달리 스스로 망을 세우기 때문이다. "0 주소의 잔액이 0 이상" 을 보던 것은 2026-09-29에 고쳤다. 잔액은 음수가 될 수 없어 언제나 참이었다. 0 주소는 어느 체인에나 있고 값이 변하지 않으므로 형식 확인에만 쓰고, 값을 실제로 읽어 오는지는 자금이 있는 노드 계정으로 본다. 송금 전후 변화는 새 계정 둘 사이에서 본다. 블록 생성 노드의 잔액은 보상·수수료로 함께 움직이기 때문이다.
- **비고**: 기존 명세: RT-A-4-02, RPC-012 / 자동 테스트: genesis-balance / PR196 우선순위: P2 / 2026-09-30에 remote-balance-check(PR196-TC-030)를 합쳐, 한 파일로 세 체인을 돈다.

## CT-RPC-008 · 체인 ID 조회

- **목적**: 모든 노드가 제네시스에 설정한 체인 ID를 돌려주는지 확인한다.
- **의존 요소**: 체인 ID, RPC 주소·API 노출
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 각 노드에서 체인 ID를 조회한다.
    2. 설정값과 비교한다.
- **기대 결과**: 모든 노드가 설정값과 같은 값을 돌려준다.
- **체인별 차이**: WEMIX3.0과 WEMIX4.0의 코드 기본값이 같으므로 체인 ID만으로 어느 체인인지 판단하지 않는다.
- **비고**: 기존 명세: RT-A-4-05, RPC-013 / 자동 테스트: chain-id, remote-chain-info (PR196-TC-029) / PR196 우선순위: P2/P3 / 자동 테스트는 체인별 설정값과 같은지 비교한다.

## CT-RPC-009 · 이벤트 로그 조회

- **목적**: 이벤트를 내는 컨트랙트를 실행한 뒤 조건에 맞는 로그가 조회되는지 확인한다.
- **의존 요소**: 테스트 계정, 컨트랙트, RPC 주소·API 노출
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 이벤트를 내는 컨트랙트를 배포하고 호출한다.
    2. 주소와 토픽으로 로그를 조회한다.
- **기대 결과**: 조건에 맞는 로그가 돌아오고 토픽이 예상값과 같다.
- **자동 테스트**: 2026-09-30에 logs-query-well-formed 와 contract-event-emitted 를 하나로 합쳤다. 둘은 체인 차이가 아니라 원본 테스트 둘이었고, 앞의 것이 뒤의 것에 그대로 들어 있었다. 토픽 비교 한 줄만 없었다. 판정은 2026-09-29에 고쳤다. 전에는 필터에 토픽을 넣고 돌아온 로그의 topic0 이 그 토픽과 같은지 봤다. 필터가 그 토픽만 골라 주므로 그 비교는 늘 참이고, 실제로는 로그가 하나라도 있는지만 확인됐다. 이제 셋으로 나눠 본다. 주소와 토픽으로 거르면 로그가 하나 나오는가, 토픽 없이 주소로만 거른 로그의 topic0 이 기대값과 같은가, 다른 토픽으로 거르면 하나도 안 나오는가. 두 번째가 토픽을 실제로 견주고, 세 번째가 필터가 거르기는 하는지 보인다.
- **비고**: 기존 명세: RT-A-4-04, RPC-014 / 자동 테스트: contract-event-emitted / PR196 우선순위: P1/P2 / 2026-09-30에 logs-query-well-formed 를 합쳤다.

## CT-RPC-010 · 서명된 트랜잭션 전송과 풀 조회

- **목적**: 직접 서명한 트랜잭션을 보내면 해시가 돌아오고 포함 전에 풀에서 보이는지 확인한다.
- **의존 요소**: 테스트 계정, RPC 주소·API 노출
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 로컬 키로 서명한 트랜잭션을 보낸다.
    2. 포함 전에 풀 내용을 조회한다.
    3. 포함 후 영수증을 조회한다.
- **기대 결과**: 해시가 돌아온다. 풀에서 보였다가 블록에 포함된다.
- **체인별 차이**: 풀 조회는 관리용 API라 공개 RPC에서는 닫혀 있을 수 있다. 그런 곳에서는 해시로 트랜잭션을 조회해 블록 번호가 비어 있는지로 "포함 전" 을 확인한다.
- **자동 테스트**: 블록 주기가 1초라 그냥 보내면 풀을 조회하기 전에 포함되므로, 생성 노드 두 대를 멈춰 합의를 세운 뒤 보낸다. 새 계정이 자기 키로 서명하고 수수료는 노드가 제안한 값을 쓴다. 풀에서 그 해시가 계정의 대기 첫 건인지, 해시 조회의 블록 번호가 비어 있는지 본다. 두 노드를 되살린 뒤 같은 해시가 성공으로 포함되고 풀의 대기가 비는지 본다.
- **비고**: 기존 명세: RT-A-4-03 / 공통 케이스(2026-09-29 신규): signed-tx-seen-in-pool / PR196 우선순위: P1 / 자동 테스트 value-transfer는 전송 부분만 대응.

## CT-RPC-011 · 트랜잭션 풀 건수 조회

- **목적**: 대기 건수와 보류 건수가 넣은 수와 맞는지 확인한다.
- **의존 요소**: 테스트 계정, RPC 주소·API 노출
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 연속 nonce 트랜잭션과 nonce 격차가 있는 트랜잭션을 넣는다.
    2. 풀 건수를 조회한다.
- **기대 결과**: 대기 건수와 보류 건수가 넣은 수와 같다.
- **자동 테스트**: 블록 주기가 1초라 넣은 트랜잭션이 곧바로 포함되므로, 생성 노드 두 대를 멈춰 합의를 세운 뒤 넣는다. 끝나면 두 노드를 되살려 대기분이 포함되는지 본다.
- **비고**: 기존 명세: RT-G-4-02, RPC-018 / 자동 테스트: txpool-status / PR196 우선순위: P1/P2

## CT-RPC-012 · 트랜잭션 풀 내용 조회

- **의존 요소**: 테스트 계정, RPC 주소·API 노출
- **분리 방식**: 설정으로 분리
- **절차**:
    1. CT-RPC-011과 같은 상태를 만든다.

- **기대 결과**: 대기 항목에 연속 nonce, 보류 항목에 격차 nonce 트랜잭션이 상세 필드와 함께 있다.
- **자동 테스트**: CT-RPC-011 과 같이 합의를 세운 뒤 넣는다. 풀 내용은 계정 단위 조회(`txpool_contentFrom`)로 읽는다. 세 클라이언트 모두 이 메서드가 있다.
- **비고**: 기존 명세: RT-G-4-03, RPC-018 / 자동 테스트: txpool-content-well-formed / PR196 우선순위: P1/P2

## CT-RPC-014 · 이벤트 로그 구독

- **목적**: 웹소켓으로 특정 주소의 이벤트를 실시간으로 받는지 확인한다.
- **의존 요소**: 테스트 계정, 컨트랙트, RPC 주소·API 노출
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 이벤트 컨트랙트를 배포한다.
    2. 그 주소로 로그 구독을 건다.
    3. 이벤트를 내는 트랜잭션을 보낸다.
- **기대 결과**: 이벤트가 바로 수신된다.
