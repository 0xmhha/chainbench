## CT-FAULT-001 · 생성 노드 1대 중단과 재시작

- **목적**: 생성 노드 하나를 멈춰도 블록이 계속 만들어지고, 다시 띄우면 따라잡는지 확인한다.
- **의존 요소**: 노드 구성·시간, 노드 직접 제어
- **분리 방식**: 별도 구현 필요
- **절차**:
    1. 블록 높이가 3 이상이 되기를 기다린다.
    2. 생성 노드 하나를 멈춘다.
    3. 다른 노드에서 블록이 계속 늘어나는지 본다.
    4. 멈춘 노드를 다시 띄우고 같은 높이의 해시와 상태 루트를 비교한다.
- **기대 결과**: 나머지 노드가 블록을 계속 만든다. 복구 노드의 해시와 상태 루트가 기준 노드와 같다.
- **체인별 차이**: 허용되는 장애 수가 다르다. WEMIX4.0과 StableNet은 검증자 3분의 2 이상이 살아 있어야 한다. WEMIX3.0은 생성 노드가 함께 운영하는 etcd 클러스터가 유지돼야 하며 과반이 살아 있어야 한다.
- **비고**: 기존 명세: RT-A-1-04, NODE-005 / 자동 테스트: fault-node-crash (PR196-TC-012), wemix-node-crash (PR196-TC-003), wbft-node-crash (PR196-TC-026), sample-lifecycle-node-restart (PR196-TC-032) / PR196 우선순위: P1/P2 / 소유한 네트워크에서만 가능.

## CT-FAULT-002 · 중단 노드 복구 후 동기화

- **목적**: 오래 멈춘 노드가 다시 뜬 뒤 최신 블록까지 동기화하는지 확인한다.
- **의존 요소**: 노드 구성·시간, 노드 직접 제어
- **분리 방식**: 별도 구현 필요
- **절차**:
    1. 노드 하나를 멈춘다.
    2. 나머지가 블록을 여러 개 만들 때까지 기다린다.
    3. 다시 띄우고 최신 해시가 일치할 때까지 기다린다.
- **기대 결과**: 최신 블록 해시가 모든 노드에서 같다.
- **체인별 차이**: CT-FAULT-001과 같다.
- **비고**: 자동 테스트: fault-node-recover (PR196-TC-013) / PR196 우선순위: P1

## CT-FAULT-003 · 생성 노드 2대 중단 시 합의 중단과 복구

- **목적**: 4대 중 2대를 멈추면 블록 생성이 멈추고, 1대를 되살리면 재개되는지 확인한다.
- **의존 요소**: 노드 구성·시간, 노드 직접 제어
- **분리 방식**: 별도 구현 필요
- **절차**:
    1. 생성 노드 2대를 멈춘다.
    2. 블록이 멈추는지 확인한다.
    3. 1대를 다시 띄우고 블록이 재개되는지 본다.
- **기대 결과**: 2대 중단 시 멈추고 1대 복구 시 재개된다.
- **체인별 차이**: 멈추는 조건이 다르다. WEMIX4.0과 StableNet은 4대 중 3대가 필요하다. WEMIX3.0은 etcd 과반 규칙이라 같은 수에서 멈추는지 따로 판정해야 한다.
- **비고**: 자동 테스트: fault-two-down (PR196-TC-015) / PR196 우선순위: P1

## CT-FAULT-004 · 네트워크 분리와 복구

- **목적**: 노드를 두 무리로 갈랐다가 다시 이으면 체인이 하나로 합쳐지는지 확인한다.
- **의존 요소**: 노드 구성·시간, 노드 직접 제어, 노드가 도는 기계의 셸과 방화벽 권한
- **분리 방식**: 별도 구현 필요
- **절차**:
    1. 생산 노드 9대를 띄우고 블록이 나오는 것을 확인한다.
    2. 4대와 5대 두 무리로 가른다. 각 노드가 도는 기계에 규칙을 넣어 상대 무리의 주소와 p2p 포트로 오가는 패킷을 떨어뜨린다.
    3. 양쪽 다 블록이 멈추는지 본다.
    4. 규칙을 걷고 다시 나아가는지, 동기화가 끝난 뒤 최신 해시가 같은지 본다.
- **기대 결과**: 분리 중 양쪽이 멈춘다. 복구 후 최신 해시가 같다.
- **체인별 차이**: 없다. 기계에서 막으므로 클라이언트의 재연결 동작과 무관하다.
- **왜 피어를 끊지 않나**: 2026-09-28 측정. `admin_addPeer` 로 들어간 상대는 static peer 가 되어 devp2p 가 끊겨도 계속 다시 건다. WEMIX3.0 은 그 위에 30초마다 거버넌스 컨트랙트를 읽어 멤버 전원에게 그 주소와 포트로 직접 거는 고리가 하나 더 있다. 연결 구성을 선언하고 가운데 다리 노드를 멈추는 방법도 같은 이유로 갈라지지 않았다 — 선언은 피어 4인데 실제로 8이 붙어 있었고, 다리는 처음부터 유일한 길이 아니었다.
- **왜 9대인가**: 8대가 살아 있어 정족수(6)를 넘는다. 그런데도 멈춘다면 노드가 빠져서가 아니라 갈라져서다. 한쪽이 4대뿐이라 6에 못 미친다.
- **어디서 도나**: 노드가 도는 기계에 셸과 방화벽 권한이 있어야 하므로 `requires` 에 `target:remote` 를 적는다. 로컬 실행은 노드가 이 기계의 프로세스라 규칙을 쓸 자리가 없고, 그 경우 건너뛴다. 무리마다 기계가 달라야 한다 — 한 기계에 두 무리의 노드가 같이 있으면 그 기계의 규칙이 둘 다에 걸리므로 거절한다.
- **비고**: 자동 테스트: fault-network-partition (PR196-TC-011) / PR196 우선순위: P1

## CT-FAULT-005 · 허브형 연결에서 합의와 전파

- **목적**: 한 노드만 나머지와 연결된 형태에서도 블록과 트랜잭션이 전파되는지 확인한다.
- **의존 요소**: 테스트 계정, 노드 구성·시간, 노드 직접 제어, RPC 주소·API 노출
- **분리 방식**: 별도 구현 필요
- **절차**:
    1. 생산 노드 4대, 종단 노드 2대, 전달 노드 1대로 띄운다. 전달 노드가 있는 구성은 연결이 proxied 로 잡혀 종단 노드가 전달 노드하고만 이어진다 — 끊어서 만드는 것이 아니라 그렇게 세운다.
    2. 피어 수로 그 모양을 확인한다.
    3. 송금을 보내고 두 종단 노드에서 잔액이 보이는지 본다. 전달 노드 말고는 길이 없다.
    4. 전달 노드를 멈춘다. 생산은 이어지고 종단 노드는 멈춘다.
    5. 다시 띄워 종단 노드가 따라잡는지 보고, 동기화가 끝난 뒤 해시를 견준다.
- **기대 결과**: 전파가 허브를 거쳐 이루어진다. 허브를 멈추면 종단 노드가 멈추고, 되살리면 따라잡아 해시가 같아진다.
- **체인별 차이**: 없다. 거버넌스에 등록되는 것은 생산 노드뿐이라 종단 노드를 자동으로 다시 이어 주는 고리가 없다.
- **왜 끊지 않나**: CT-FAULT-004와 같은 이유다. 2026-09-29 측정에서 `admin_removePeer` 로 끊은 피어가 다시 붙어, 같은 체인에서도 실행마다 spoke 피어 수가 1에서 3까지 흔들렸다.
- **비고**: 자동 테스트: fault-p2p-topology (PR196-TC-014) / PR196 우선순위: P1

## CT-FAULT-006 · 생산 노드 중단 시 대기 트랜잭션 처리

- **목적**: 트랜잭션을 받은 노드가 멈춰도 다른 노드가 그 트랜잭션을 처리하는지 확인한다.
- **의존 요소**: 테스트 계정, 노드 구성·시간, 노드 직접 제어, RPC 주소·API 노출
- **분리 방식**: 별도 구현 필요
- **절차**:
    1. 노드 1에 송금을 보낸다.
    2. 노드 1을 멈춘다.
    3. 노드 2에서 블록 진행과 풀 대기 건수를 확인한다.
- **기대 결과**: 블록이 진행되고 대기 건수가 0이 된다.
- **체인별 차이**: CT-FAULT-001과 같다.
- **비고**: 자동 테스트: fault-txpool-leader-change (PR196-TC-016) / PR196 우선순위: P1
