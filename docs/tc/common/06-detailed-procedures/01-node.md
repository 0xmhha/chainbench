## CT-NODE-001 · 노드 기동과 블록 생성

- **목적**: 세 체인 각각 노드를 띄웠을 때 블록이 만들어지고 노드끼리 연결되는지 확인한다.
- **의존 요소**: 체인 ID, 노드 구성·시간, 노드 프로그램, RPC 주소·API 노출
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 블록 생성 노드 4대로 네트워크를 띄운다.
    2. 블록 높이가 2 이상이 될 때까지 기다린다.
    3. 체인 ID, 블록 높이, 연결된 피어 수를 조회한다.
- **기대 결과**: 체인 ID가 설정값과 같다. 블록 높이가 2 이상이다. 피어 수가 0이 아니다.
- **체인별 차이**: WEMIX4.0과 StableNet은 검증자 목록 조회로 생산자 수를 함께 확인할 수 있다. WEMIX3.0은 해당 조회가 없어 관리 API로 확인한다.
- **비고**: 자동 테스트: wemix-chain-up (PR196-TC-001), wbft-chain-up (PR196-TC-023), stablenet-chain-up (PR196-TC-020) / PR196 우선순위: P1/P2 / 검증자 수 확인은 체인마다 방법이 다르다.

## CT-NODE-002 · 15노드 구성 기동

- **목적**: 블록 생성 노드 13대와 전달·종단 노드로 큰 구성을 띄웠을 때도 블록이 만들어지는지 확인한다.
- **의존 요소**: 노드 구성·시간, 노드 프로그램, RPC 주소·API 노출
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 블록 생성 노드 13대, 전달 노드 1대, 종단 노드 1대로 네트워크를 띄운다.
    2. 블록 높이가 2 이상이 될 때까지 기다린다.
    3. 체인 ID, 블록 높이, 피어 수를 조회한다.
- **기대 결과**: CT-NODE-001과 같다. 검증자 수가 13이다(WEMIX3.0은 검증자 조회가 없어 생략).
- **체인별 차이**: WEMIX3.0은 전달 노드 없이 종단 노드 2대 구성을 쓴다. 기동 대기 시간이 더 길다.
- **비고**: 자동 테스트: wemix-chain-up-15 (PR196-TC-002), wbft-chain-up-15 (PR196-TC-024), stablenet-chain-up-15 (PR196-TC-021) / PR196 우선순위: P1/P2

## CT-NODE-003 · 제네시스 초기화와 블록 0 해시 일치

- **목적**: 제네시스 파일로 초기화한 모든 노드의 블록 0 해시가 같고, 체인 ID가 제네시스 값과 같은지 확인한다.
- **의존 요소**: 체인 ID, 노드 프로그램, 노드 구성·시간
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 체인별 제네시스로 모든 노드를 초기화하고 기동한다.
    2. 각 노드에서 블록 0을 조회한다.
    3. 체인 ID를 조회한다.
- **기대 결과**: 모든 노드의 블록 0 해시가 같다. 블록 0의 이전 블록 해시가 0이다. 체인 ID가 제네시스 값과 같다.
- **체인별 차이**: WEMIX3.0은 제네시스를 노드 프로그램이 거버넌스 설정에서 만든다. WEMIX4.0과 StableNet은 템플릿에 검증자 정보를 채워 만든다. 기대 해시는 체인·구성마다 다르다.
- **비고**: 기존 명세: RT-A-1-01, RT-A-1-01-B, TC-5-3-01, TS-5-3-01 / 자동 테스트: genesis-block-hash-consistent, chain-id / PR196 우선순위: P1/P2/P3 / RT-A-1-01-A(테스트넷 내장 제네시스)는 StableNet 전용이라 제외.

## CT-NODE-004 · Full Sync 동기화

- **목적**: 새 노드가 모든 블록을 실행하며 기존 체인을 따라잡는지 확인한다.
- **의존 요소**: 노드 구성·시간, 노드 프로그램, 노드 직접 제어
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 기존 노드의 블록 높이가 새 노드보다 2 이상 높은 상태를 만든다.
    2. 새 노드를 full 동기화 방식으로 기동한다.
    3. 같은 높이에서 블록 해시와 상태 루트를 비교한다.
- **기대 결과**: 새 노드의 블록 해시와 상태 루트가 기존 노드와 같다.
- **체인별 차이**: 기본 동기화 방식이 WEMIX3.0은 snap, 나머지 둘은 full이라 방식을 명시해야 한다. WEMIX3.0은 블록 생성 노드끼리 별도 동기화 점검이 끼어들므로 생산에 참여하지 않는 노드에서 관찰한다.
- **비고**: 기존 명세: RT-A-1-02, NODE-003 / PR196 우선순위: P0

## CT-NODE-005 · Snap Sync 동기화

- **목적**: 새 노드가 상태 스냅샷으로 동기화한 뒤 잔액 조회가 되는지 확인한다.
- **의존 요소**: 노드 구성·시간, 노드 프로그램, 노드 직접 제어
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 기존 체인에 블록 128개 이상을 쌓는다.
    2. 새 노드를 snap 동기화 방식으로 기동한다.
    3. 동기화 완료 후 잔액과 상태 루트를 비교한다.
- **기대 결과**: 상태 동기화가 끝나고 잔액 조회가 된다. 상태 루트가 기존 노드와 같다. full 방식으로 바뀌어 끝난 경우는 통과로 보지 않는다.
- **체인별 차이**: CT-NODE-004와 같다.
- **비고**: 기존 명세: RT-A-1-03, NODE-004 / PR196 우선순위: P1

## CT-NODE-006 · 누락 블록 일괄 동기화

- **목적**: 연결이 끊겨 블록 격차가 2 이상 생긴 노드가 다시 연결됐을 때 누락 블록을 순서대로 받아오는지 확인한다.
- **의존 요소**: 노드 구성·시간, 노드 직접 제어
- **분리 방식**: 별도 구현 필요
- **절차**:
    1. 노드 하나를 네트워크에서 분리한다.
    2. 나머지 노드가 블록을 2개 이상 더 만들 때까지 기다린다.
    3. 다시 연결하고 블록 높이가 같아질 때까지 기다린다.
    4. 같은 높이의 블록과 상태를 비교한다.
- **기대 결과**: 분리됐던 노드가 누락 블록을 받아 높이와 해시가 일치한다.
- **체인별 차이**: 어느 경로로 받았는지는 노드 로그로 확인한다. 로그 문구가 체인마다 다르다.
- **비고**: 기존 명세: RT-A-1-06 / PR196 우선순위: P0

## CT-NODE-007 · 새 블록 실시간 수신

- **목적**: 정상 운영 중인 노드가 다른 노드가 만든 새 블록을 전파로 받아 바로 반영하는지 확인한다.
- **의존 요소**: 노드 구성·시간

- **기대 결과**: 새 블록이 만들어진 직후 관찰 노드의 높이가 따라 올라간다.

## CT-NODE-008 · 피어 연결과 피어 조회

- **목적**: 노드들이 부트노드를 거쳐 서로 연결되고, 피어 수와 피어 정보를 조회할 수 있는지 확인한다.
- **의존 요소**: RPC 주소·API 노출, 노드 구성·시간
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 부트노드 설정으로 노드들을 기동한다.
    2. 각 노드에서 피어 수를 조회한다.
    3. 피어 상세 정보를 조회한다.
- **기대 결과**: 모든 노드의 피어 수가 1 이상이다. 피어 정보에 상대 노드가 보인다.
- **체인별 차이**: 피어 상세 조회는 관리용 API라 운영망 공개 RPC에서는 닫혀 있을 수 있다.
- **비고**: 기존 명세: RT-A-1-05, RT-G-4-01, RT-G-4-04, RPC-019 / 자동 테스트: basic-peers (PR196-TC-006), admin-peers-populated / PR196 우선순위: P1/P2

## CT-NODE-010 · 전달 노드 경유 동기화

- **목적**: 종단 노드가 생성 노드와 직접 연결되지 않고 전달 노드만 거쳐도 블록을 받는지 확인한다.
- **의존 요소**: 노드 구성·시간
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 생성 노드, 전달 노드, 종단 노드를 계층으로 연결한다.
    2. 종단 노드의 블록 높이가 올라가는지 확인한다.
    3. 각 노드의 피어 수로 연결 형태를 확인한다.
- **기대 결과**: 종단 노드의 높이가 올라간다. 종단 노드의 피어는 전달 노드 하나뿐이다.
- **체인별 차이**: 실행 도구의 WEMIX3.0 구성도 전달 노드 역할을 받는다.
- **비고**: 자동 테스트: stablenet-proxied-pn-routing (PR196-TC-033), wbft-proxied-routing / PR196 우선순위: P2

## CT-NODE-011 · 종단 노드가 먼저 오는 혼합 배치

- **목적**: 첫 번째 노드가 종단 노드인 배치에서도 생산자 수가 설정대로인지 확인한다.
- **의존 요소**: 노드 구성·시간, RPC 주소·API 노출
- **분리 방식**: 별도 구현 필요
- **절차**:
    1. 종단 노드 1대, 생성 노드 3대를 그 순서로 배치해 기동한다.
    2. 생산자 수를 조회한다.
    3. 블록이 계속 만들어지는지 확인한다.
- **기대 결과**: 생산자 수가 3이다. 블록이 계속 만들어진다.
- **체인별 차이**: 생산자 수 조회 방법이 체인마다 다르다(CT-NODE-001 참고).
- **비고**: 자동 테스트: e1-mixed-producers (PR196-TC-025) / PR196 우선순위: P2

## CT-NODE-012 · 노드 프로그램 교체 후 서명 호환

- **목적**: 노드 프로그램을 새 버전으로 바꿔도 이전에 처리한 트랜잭션이 그대로 조회되는지 확인한다.
- **의존 요소**: 노드 프로그램, 노드 직접 제어
- **분리 방식**: 별도 구현 필요
- **절차**:
    1. 트랜잭션을 보내고 영수증을 저장한다.
    2. 노드 하나의 프로그램을 새 버전으로 바꿔 재기동한다.
    3. 같은 트랜잭션의 영수증과 내용을 다시 조회해 비교한다.
- **기대 결과**: 블록 번호, 상태, 보낸 이, 받는 이가 교체 전과 같다.
- **체인별 차이**: 교체할 프로그램 파일과 버전 표기가 체인마다 다르다.
- **비고**: 기존 명세: TC-3-1-04 / 자동 테스트: signature-compat-across-swap / PR196 우선순위: P1

## CT-NODE-013 · 제네시스 불일치 시 기동 거부

- **목적**: 저장된 체인과 다른 제네시스로 노드를 다시 띄우면 기동을 거부하는지 확인한다.
- **의존 요소**: 노드 프로그램, 노드 직접 제어
- **분리 방식**: 별도 구현 필요
- **절차**:
    1. 정상 운영 중인 노드 하나를 멈춘다.
    2. 제네시스 값을 바꿔 다시 띄운다.
    3. 기동 실패 로그를 확인하고 나머지 노드가 계속 블록을 만드는지 본다.
- **기대 결과**: 바꾼 노드는 제네시스 불일치로 기동하지 못한다. 나머지 노드는 영향이 없다.
- **체인별 차이**: 제네시스 불일치 오류 문구는 세 클라이언트가 같다(database contains incompatible genesis). 노드를 멈추고 다시 띄우는 제어가 필요해 우리가 띄운 네트워크에서만 된다.
- **비고**: 기존 명세: TC-4-1-03, TS-4-1-02 / 자동 테스트: genesis-mismatch-refuses-to-start / PR196 우선순위: P1

## CT-NODE-015 · 블록 시각 단조 증가

- **목적**: 연속 블록의 시각이 거꾸로 가지 않는지 확인한다.
- **의존 요소**: RPC 주소·API 노출

## CT-NODE-016 · 블록 생성 주기

- **목적**: 연속 블록의 시각 차이가 설정한 주기와 같은지 확인한다.
