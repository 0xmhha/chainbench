## CT-TX-001 · 일반 송금

- **목적**: 계정 간 송금이 블록에 포함되고 받는 쪽 잔액이 늘어나는지 확인한다.
- **의존 요소**: 테스트 계정, RPC 주소·API 노출
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 받을 계정을 새로 만든다.
    2. 노드 계정에서 송금한다.
    3. 영수증과 받는 계정 잔액을 조회한다.
- **기대 결과**: 영수증 상태가 성공이다. 받는 계정 잔액이 보낸 금액만큼 늘어난다.
- **비고**: 기존 명세: TX-001, RT-A-4-03 / 자동 테스트: basic-tx-send (PR196-TC-009), sample-minimal-value-transfer (PR196-TC-031), value-transfer / PR196 우선순위: P1/P2 / RT-A-4-03은 서명된 트랜잭션 전파 부분만 대응.

## CT-TX-002 · Legacy 트랜잭션

- **목적**: gasPrice 필드만 쓰는 예전 형식 트랜잭션이 처리되는지 확인한다.
- **의존 요소**: 테스트 계정, 수수료 값
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. gasPrice를 정해 예전 형식으로 서명·전송한다.
    2. 영수증과 트랜잭션 형식을 조회한다.
    3. 보낸 계정 잔액 변화를 계산한다.
- **기대 결과**: 상태가 성공이고 형식이 0x0이다. 잔액 변화가 송금액과 수수료의 합과 같다.
- **체인별 차이**: 실제 적용 가스 가격이 StableNet 일반 계정에서는 블록 헤더의 팁으로 바뀐다. 기대 수수료는 체인별로 계산한다.
- **자동 테스트**: 새 계정이 자기 키로 legacy 를 서명해 보낸다. 가스 가격은 `eth_gasPrice` 로 읽는다(세 체인 모두 풀의 하한을 넘는다). 수수료는 영수증의 gasUsed × effectiveGasPrice 로 구해, 적용 가격 규칙이 체인마다 달라도 같은 식으로 잔액을 확인한다. 받는 계정의 잔액도 송금액만큼 늘었는지 본다.
- **비고**: 기존 명세: RT-A-2-01, TX-006 / 자동 테스트: legacy-transfer (StableNet 전용) / 공통 케이스(2026-09-29 신규): legacy-value-transfer / PR196 우선순위: P1

## CT-TX-003 · 동적 수수료 트랜잭션

- **목적**: 최대 수수료와 팁을 지정하는 형식의 트랜잭션이 처리되는지 확인한다.
- **의존 요소**: 테스트 계정, 수수료 값
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 최대 수수료를 기본 수수료와 팁의 합 이상으로 정해 전송한다.
    2. 영수증과 형식을 조회한다.
- **기대 결과**: 상태가 성공이고 형식이 0x2다. 실제 적용 가스 가격이 규칙대로 계산된다.
- **체인별 차이**: CT-TX-002와 같다. 팁을 `eth_maxPriorityFeePerGas` 로 읽으면 세 체인 모두 실제 적용 가격이 "포함 블록의 기본 수수료 + 그 팁" 이 된다. StableNet 은 이 RPC 가 헤더 팁과 같은 거버넌스 팁을 돌려주고, WEMIX3.0 은 거버넌스 팁을, WEMIX4.0 은 가격 오라클 추정값을 돌려준다.
- **자동 테스트**: 새 계정이 최대 수수료를 "최신 기본 수수료 × 2 + 팁" 으로 정해 보낸다. 형식 0x2 와 성공 상태, 실제 적용 가격이 포함 블록의 기본 수수료와 팁의 합인지, 보낸 계정 잔액이 송금액과 수수료만큼 줄었는지 본다.
- **비고**: 기존 명세: RT-A-2-02, TX-003 / 자동 테스트: dynamic-fee-tx (StableNet 전용) / 공통 케이스(2026-09-29 신규): dynamic-fee-transfer / PR196 우선순위: P1

## CT-TX-005 · 수수료 대납 트랜잭션

- **목적**: 보내는 계정과 수수료를 내는 계정이 다른 트랜잭션이 처리되는지 확인한다.
- **의존 요소**: 테스트 계정, 수수료 값, 하드포크 활성
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 보낼 계정과 대납 계정을 만들어 자금을 넣는다.
    2. 두 계정이 각각 서명한 대납 트랜잭션을 전송한다.
    3. 영수증과 두 계정의 잔액을 조회한다.
- **기대 결과**: 상태가 성공이고 형식이 0x16이다. 보낸 계정은 송금액만 줄고 대납 계정은 수수료만 준다.
- **체인별 차이**: 대납 계정 잔액 검사 기준이 다르다. WEMIX4.0과 StableNet은 조건에 따라 가스 가격 기준으로 검사하고, StableNet은 대납 계정의 차단 여부도 본다.
- **비고**: 기존 명세: RT-D-01, TX-004 / 자동 테스트: fee-delegated-transfer / PR196 우선순위: P1

## CT-TX-008 · 대납자 잔액 부족 거부

- **목적**: 대납 계정 잔액이 수수료보다 적으면 거부되는지 확인한다.
- **의존 요소**: 테스트 계정, 수수료 값
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 잔액이 없는 대납 계정으로 대납 트랜잭션을 전송한다.
    2. 응답과 블록 포함 여부를 확인한다.
- **기대 결과**: 거부되고 블록에 포함되지 않는다.
- **체인별 차이**: StableNet 명세는 실행 단계 거부라고 적었으나 세 클라이언트 모두 풀 진입 단계에서 먼저 거부한다. 잔액 기준(최대 수수료인지 가스 가격인지)이 체인·조건별로 다르다.
- **비고**: 기존 명세: RT-D-05, TX-016 / 자동 테스트: feepayer-insufficient-rejected / PR196 우선순위: P1

## CT-TX-010 · 접근 목록을 붙인 대납 트랜잭션

- **목적**: 접근 목록이 있는 트랜잭션을 대납 형식으로 조립해도 처리되는지 확인한다.
- **의존 요소**: 테스트 계정
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 접근 목록을 붙인 트랜잭션을 보낸 이가 서명한다.
    2. 대납자가 대납 형식으로 조립해 전송한다.
    3. 접근 목록이 없는 대납 트랜잭션도 함께 보낸다.
- **기대 결과**: 두 트랜잭션 모두 블록에 포함되고 상태가 성공이다.
- **체인별 차이**: 세 클라이언트 모두 대납 형식에 접근 목록을 복사하는 경로가 있다. 대납 형식은 Applepie 하드포크부터 받는다.
- **자동 테스트**: T-2 가 겨냥한 복사(SetSenderTx)는 노드가 `eth_signRawFeeDelegateTransaction` 으로 조립할 때만 일어나므로 노드가 조립하게 한다. node1 이 `eth_signTransaction` 으로 접근 목록을 붙인 동적 수수료 트랜잭션에 서명하고, node2 가 대납 서명을 붙이고, `eth_sendRawTransaction` 으로 보낸다. 성공 상태, 형식 0x16, 대납자, 복사된 접근 목록을 본다. 접근 목록 없는 대납도 같은 방법으로 한 건 보낸다. 노드 키 저장소를 쓰므로 소유한 네트워크에서만 돈다.
- **비고**: 기존 명세: T-2 / 공통 케이스(2026-09-29 신규): fee-delegated-access-list / StableNet과 WEMIX4.0 2차 변경 테스트에 같은 번호로 있다.

## CT-TX-011 · 노드 키 저장소 경유 대납 서명

- **목적**: 노드의 키 저장소로 대납 트랜잭션을 서명·전송하는 경로가 동작하는지 확인한다.
- **의존 요소**: 테스트 계정, RPC 주소·API 노출
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 노드에 잠금 해제된 계정으로 대납 트랜잭션 전송을 요청한다.
    2. 조립할 수 없는 대납 요청이 거부되는지 확인한다.
- **기대 결과**: 정상 요청은 처리된다. 대납자가 없는 요청과 보낸 이 트랜잭션이 동적 수수료 형식이 아닌 요청은 거부된다.
- **체인별 차이**: 세 클라이언트 모두 키 저장소가 대납 형식을 서명하고, 위 두 거부를 같은 문구(`missing FeePayer`, `senderTx type error`)로 한다. 대납자 키로 서명할 때 트랜잭션 형식이 맞지 않으면 거부하는 검사(PR #114)는 WEMIX3.0 에 없어 공통에서 뺐다(부록 A).
- **자동 테스트**: node1 이 키 저장소로 보낸 이 서명을, node2 가 키 저장소로 대납 서명을 붙여 보낸다. 성공 상태, 형식 0x16, 대납자, 보낸 이를 본다. 거부 두 가지는 `eth_signRawFeeDelegateTransaction` 이 정해진 문구의 오류로 답하는지로 본다.
- **비고**: 기존 명세: T-3 (부분 대응) / 공통 케이스(2026-09-29 신규): keystore-fee-delegate-sign / 공개 RPC에는 잠금 해제 계정이 없어 소유한 네트워크에서만 가능.

## CT-TX-012 · 계정별 nonce 순서 보장

- **목적**: 한 계정에서 nonce 역순으로 보낸 트랜잭션이 오름차순으로 블록에 포함되는지 확인한다.
- **의존 요소**: 테스트 계정, 수수료 값
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 새 계정에 자금을 넣는다.
    2. nonce 2, 1, 0 순서로 트랜잭션을 전송한다.
    3. 계정 nonce가 3이 될 때까지 기다린다.
- **기대 결과**: 세 트랜잭션이 모두 포함되고 nonce가 3이다. 해시 중복이나 누락이 없다.
- **비고**: 기존 명세: RT-A-2-04, TX-010 / 자동 테스트: nonce-ordering / PR196 우선순위: P0/P1

## CT-TX-013 · 같은 nonce 트랜잭션 교체

- **목적**: 대기 중인 트랜잭션을 같은 nonce에 더 높은 수수료로 다시 보내면 새 것만 포함되는지 확인한다.
- **의존 요소**: 테스트 계정, 수수료 값
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. nonce 격차를 두어 대기 상태 트랜잭션을 만든다.
    2. 같은 nonce로 수수료를 10% 넘게 올린 트랜잭션을 보낸다.
    3. 격차를 채우는 트랜잭션을 보내 처리되게 한다.
- **기대 결과**: 나중 트랜잭션만 블록에 포함되고 처음 것은 영수증이 없다.
- **체인별 차이**: 교체에 필요한 인상 비율(기본 10%)은 노드 설정값이라 프로필로 둔다.
- **비고**: 기존 명세: RT-A-2-09, TX-013 / 자동 테스트: replacement-tx / PR196 우선순위: P1

## CT-TX-014 · 미포함 트랜잭션의 이월과 교체

- **목적**: 블록에 들어가지 못한 트랜잭션이 풀에 남아 다음 블록에 순서대로 들어가고, 교체하면 새 것만 들어가는지 확인한다.
- **의존 요소**: 테스트 계정, 수수료 값
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 블록에 다 들어가지 못할 만큼 트랜잭션을 보낸다.
    2. 남은 트랜잭션이 풀에 있는지 확인한다.
    3. 그중 하나를 수수료를 올려 교체한다.
    4. 다음 블록들의 포함 순서를 확인한다.
- **기대 결과**: 남은 트랜잭션이 nonce 순서대로 포함된다. 교체한 nonce에는 새 트랜잭션만 들어간다.
- **체인별 차이**: 블록 크기 한도로 넘치게 하는 방법은 WEMIX3.0 한 브랜치(PR196)에만 있다. 가스 한도로 넘치게 하는 방법은 세 체인 공통이다.
- **자동 테스트**: 남은 가스가 10000 이하가 될 때까지 도는 컨트랙트를 부르고, 각 트랜잭션의 가스 한도를 "최신 블록 가스 한도 − 1000000" 으로 잡는다. 가스를 실제로 거의 다 쓰므로 한 블록에 한 건만 들어간다. nonce 0~5 를 기다리지 않고 보낸 뒤 풀의 대기 건수가 2 이상인지 보고, 마지막 nonce 를 팁과 최대 수수료를 두 배로 올려 교체한다. 여섯 건이 모두 성공하고 포함 블록 번호가 nonce 순서대로 늘며 교체 전 해시는 사라졌는지 본다. genesis 가스 한도는 덮어쓰지 않고 체인 기본값을 쓴다(WEMIX3.0 은 메인넷과 같은 105000000). 가스를 최신 블록 한도에서 구하므로 한도가 달라도 이월은 같은 식으로 생긴다. 한도를 낮춰 두면 WEMIX3.0 이 체인을 올릴 때 거버넌스 컨트랙트 배포가 블록 한도에 걸려 끝나지 않는다(2026-09-30, 10000000 에서 확인).
- **비고**: 기존 명세: N-008 / 공통 케이스(2026-09-29 신규): carry-over-and-replace / PR196 신규 테스트. 관측 부분만 공통.

## CT-TX-015 · 잔액 부족 트랜잭션 거부

- **목적**: 잔액보다 큰 금액을 보내면 풀 진입 단계에서 거부되는지 확인한다.
- **의존 요소**: 테스트 계정
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 잔액에 1을 더한 금액으로 송금한다.
    2. 응답과 블록 진행을 확인한다.
- **기대 결과**: 거부된다. 보낸 계정의 잔액과 nonce는 그대로다. 블록은 계속 만들어진다.
- **체인별 차이**: 거부 문구의 앞부분(잔액 부족)은 같고 뒤에 붙는 설명이 다르다. 거부 이유까지 확인하려면 문구 앞부분으로 판정한다.
- **비고**: 기존 명세: RT-A-2-06, TX-011 / 자동 테스트: insufficient-funds-rejected, wbft-insufficient-funds-rejected, wemix-insufficient-funds-rejected / PR196 우선순위: P1 / 세 체인용 자동 테스트가 이미 있다.

## CT-TX-016 · 블록 가스 한도 초과 트랜잭션 거부

- **목적**: 가스 한도를 블록 한도보다 크게 잡으면 거부되는지 확인한다.
- **의존 요소**: 수수료 값
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 최신 블록의 가스 한도를 조회한다.
    2. 그보다 1 큰 가스 한도로 전송한다.
    3. 응답을 확인한다.
- **기대 결과**: 거부된다.
- **체인별 차이**: CT-TX-015와 같다.
- **비고**: 기존 명세: RT-A-2-07, TX-012 / 자동 테스트: gas-limit-exceeds-block-rejected, gaslimit-exceeded-rejected / PR196 우선순위: P1

## CT-TX-017 · 거부와 실행 실패의 상태 구분

- **목적**: 풀에서 거부된 트랜잭션과 블록에 들어가 실행에 실패한 트랜잭션이 각각 올바른 상태로 남는지 확인한다.
- **의존 요소**: 테스트 계정, 컨트랙트
- **분리 방식**: 설정으로 분리, 기대값은 체인별 계산
- **절차**:
    1. 거부될 트랜잭션(잔액 부족)과 실행에 실패할 트랜잭션(되돌림, 가스 소진)을 보낸다.
    2. 풀, 블록, 영수증을 조회한다.
- **기대 결과**: 거부된 것은 풀과 블록에 없다. 실행에 실패한 것은 블록에 있고 영수증 상태가 실패다.
- **자동 테스트**: 한 계정에서 잔액보다 1 wei 많은 송금, 되돌리는 컨트랙트 호출, 가스를 다 쓰는 컨트랙트 호출을 차례로 보낸다. 거부된 것은 해시가 남지 않으므로 계정 단위로 본다(nonce 와 잔액이 그대로, 풀의 대기·보류가 비어 있음). 실패한 둘은 영수증 상태 0x0 과 블록 번호가 있고, nonce 가 2 늘며 잔액이 두 건의 수수료만큼 준다.
- **비고**: 기존 명세: N-009 / 공통 케이스(2026-09-29 신규): reject-vs-execution-failure / PR196 신규 테스트. 관측 부분만 공통.

## CT-TX-019 · 부하 전송 중 블록 진행

- **목적**: 블록마다 일정 비율의 가스를 쓰는 트랜잭션을 계속 보내도 블록이 진행되는지 확인한다.
- **의존 요소**: 테스트 계정, 컨트랙트, 노드 직접 제어
- **분리 방식**: 별도 구현 필요
- **절차**:
    1. 블록 가스의 30%를 쓰는 트랜잭션을 15블록 동안 보낸다.
    2. 블록이 계속 만들어지는지 확인한다.
- **기대 결과**: 블록이 멈추지 않는다.
- **체인별 차이**: 부하용 컨트랙트 코드는 최신 명령어를 쓰지 않아 세 체인에서 실행된다. 처리량 측정은 아니다.
- **비고**: 자동 테스트: stress-tx-flood (PR196-TC-018) / PR196 우선순위: P1

## CT-TX-020 · 테스트 계정 자금 지급

- **목적**: 새 계정에 노드 계정으로 자금을 넣는 준비 절차가 동작하는지 확인한다.
- **의존 요소**: 테스트 계정
- **분리 방식**: 설정으로 분리
- **절차**:
    1. 새 계정을 만든다.
    2. 노드 계정에서 정해진 금액을 보낸다.
    3. 잔액을 조회한다.
- **기대 결과**: 잔액이 보낸 금액 이상이다.
- **체인별 차이**: 노드 계정 서명은 소유한 네트워크에서만 된다. 공개 RPC에서는 자금이 있는 운영 계정과 로컬 서명이 필요하다.
- **비고**: 자동 테스트: stablenet-faucet-funds (PR196-TC-037) / PR196 우선순위: P3 / 다른 테스트의 준비 절차로도 쓰인다.
