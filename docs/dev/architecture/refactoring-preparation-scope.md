## 3. 문서 그래프 — 사용자 확정

문서·절의 의미 구조에 기존 저장소의 X-bar 사상을 적용하고 근거 구절을 연결한다.

| 역할 | 의미 |
|---|---|
| X⁰ / Head | 문서·절의 중심 주제 또는 주장 |
| Complement | 그 주제·계약이 성립하는 데 필요한 조건·논항 |
| Adjunct | 선택적인 보충 설명·수식 |
| Specifier | 대상·환경·맥락을 특정하는 정보 |

개별 자연어 문장 내부의 언어학적 구문 트리는 만들지 않는다.
기존 사상의 출처는 `docs/dev/dsl-v2-proposal.md` §2.1이다.

수행 제안:
- 문서 인벤토리와 각 분류의 파일·절·근거 위치를 보존한다.
- `docs/README.md`의 문서 권위·현행/이력 구분을 X-bar 역할과 별도로 기록한다.
- 과거 측정과 폐기된 제안을 현재 요구나 현재 결함으로 취급하지 않는다.
- 주제 혼재, 필수 근거 누락, 중복·충돌을 기록하고 해석이 불확실한 분류를 표시한다.

## 4. 코드 그래프 — 사용자 확정

chainbench 전체 심볼, 정적으로 확인 가능한 함수·메서드 호출과 인터페이스 구현 관계를 분석한다.
전체 패키지 의존성만 생성하고 주요 흐름만 상세 분석하는 축소안은 사용하지 않는다.

수행 제안:
- AST와 필요한 타입 정보를 사용하고, 기존 생성기는 실제 지원 범위를 확인하여 재사용한다.
- 패키지·심볼 참조, 호출, 인터페이스 구현 가능 관계를 서로 다른 관계로 기록한다.
- 동적 디스패치 후보와 미해결 호출을 확정 호출로 표시하지 않는다.
- 소스 인벤토리에 제품·테스트·생성 코드와 빌드 조건을 구분하고 분석·제외·실패 사유를 기록한다.
- 저장소·기준 커밋·작업 트리 상태·파일 위치·분석 조건을 추적할 수 있게 한다.
  세 체인은 Go 모듈 이름이 같으므로 모듈 이름만으로 식별하지 않는다.
- 재생성 가능한 원시 그래프와 전체 개요·기능별 상세 뷰를 함께 제공한다.

## 5. 진단과 계획 — 사용자 확정

문서 그래프와 코드 그래프를 대조하여 근거 있는 구조 진단, 목표 구조, 단계별 리팩토링 계획과
검증 기준·실행 절차를 산출한다.

수행 제안:
- 문제마다 문서 근거, 코드 심볼·관계, 현재 영향, 불확실성을 연결한다.
- 패키지 크기나 fan-in/fan-out만으로 응집도 저하를 단정하지 않는다.
- 기능 응집도, 의존 방향, 책임 중복, 상태 소유권, 구성·테스트 경계와 생명주기를 함께 검토한다.
- 목표 구조에 책임 소유자, 허용 의존, 주요 인터페이스, 상태·증적의 소유권을 명시한다.
- 각 이행 단계에 선행 조건, 변경 대상, 보존 계약, 검증 방법, 실패 시 복구 방법을 붙인다.
- 기존 설계·통폐합 계획을 현재 코드와 대조하고 유지·수정·폐기 제안의 이유를 남긴다.

별도 대안을 문서에 포함하는 것은 특정 비호환 변경의 실제 적용을 승인한 것으로 간주하지 않는다.

## 7. 검증 경계와 준비 완료 기준

**사용자 확정:** 이번에는 기존 테스트·기록을 근거로 검증 항목과 실행 절차까지 준비한다.
실제 세 체인 E2E 실행과 현재 동작 기준선 확보는 이후 작업이다.

이번 산출물의 검증 제안:
1. 문서·코드 인벤토리와 그래프 분석 범위를 대조하고 누락·실패·제외를 설명한다.
2. 그래프 식별자·참조 무결성·근거 위치·관계 종류를 검증하고 재생성 절차를 제공한다.
3. 분석 도구를 추가·확장하는 경우 필요한 무결성·관계 정확성 검증을 함께 작성하고 실행한다.
4. 진단에서 목표 구조·이행 단계·검증 항목까지 근거 추적이 가능한지 확인한다.
5. 검증 계획은 체인별 시나리오, 명령, 필요 바이너리·환경, 기대 결과와 실패·SKIP 판정을 명시한다.
   기존 검사와 새로 작성해야 할 검사를 구분한다.
6. 과거 테스트 기록과 이번에 직접 확인한 사실을 구별한다.
   실제 기준선은 미확보 상태로 표시하고 후속 착수 단계에 배치한다.

`tests/README.md`와 `tests/e2e/README.md`에 따르면 실제 체인 E2E는 별도 `e2e` 빌드 태그로
실행하며 바이너리가 없으면 SKIP할 수 있다. 따라서 일반 `go test ./...` 성공이나 E2E SKIP을
세 체인 라이브 검증 성공으로 간주하지 않는다. 구체적인 명령·시나리오는 준비 작업에서 현재 코드와
대조하여 검증 절차로 작성한다.
