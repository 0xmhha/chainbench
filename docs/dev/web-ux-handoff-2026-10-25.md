- 좁은 화면에서 단언 표는 칸 이름과 값을 쌓은 목록이 되고, 로그 레벨은 색만이 아니라 첫 글자도 보인다.

### #461 기관 일지 테마와 기록계 띠

impeccable 신규 작업 절차로 시안 셋(기관 일지, 로직 분석기, 출발 안내판)을 만들어 보였고, 사용자가
"테마와 배치는 첫째(기관 일지), 데이터를 읽는 방식은 둘째(로직 분석기)"로 섞기로 정했다.

- **공용 테마.** 녹회색 장부 용지에 1px 괘선, 직각 모서리, condensed 글꼴의 칸 이름을 쓴다. 빨간 잉크는
  잘못된 것에만 쓴다. 밝은 판과 어두운 판이 있고 `prefers-color-scheme`를 따른다. 글자색 대비는 두 판 모두
  4.5:1 이상이다. 시각 기준은 새로 만든 [`web/DESIGN.md`](../../web/DESIGN.md)에 있다.
- **상태 표시.** 유니코드 글자(✓ ✕ ●) 대신 SVG로 그린 표시(`StatusMark`)를 쓴다.
- **작업 상세.** 위에서부터 머리줄, 사고 기록, 기록계 띠, 로그와 계기 기록표, 테스트 기록, 단계별 당직
  기록 순서다.
  - 기록계 띠는 테스트, 노드의 경고와 오류, 블록 높이, 피어, 대기 tx, 다른 노드의 오류를 한 시간축에 쌓는다.
    A와 B 두 커서 사이의 변화를 측정 칸에 보인다.
  - 계기 기록표와 측정 칸은 다른 모든 노드와 어긋난 값을 빨간 원으로 두른다. 값이 바뀌었다는 이유만으로는
    빨갛게 하지 않는다.
  - 계산은 `web/src/recorder.mjs`의 순수 함수에 있고 `tests/webui/recorder.test.mjs`가 덮는다.

## 4. 이번 작업(#460, #461)에서 처리하지 못한 것

critique 디자인 리뷰가 지적했지만 고치지 않은 것과, 작업하면서 남긴 것을 적는다.

**작업 상세 안에서**

- 실행 중인 작업에 흐르는 경과 시간이 없고, 기록계 띠도 실시간으로 늘어나지 않는다.
- 단계가 실패한 화면에서 띠에 단계 구간을 보이는 채널이 없다. 지금은 단계 시간창으로 띠를 자르기만 한다.
- 다음 오류로 커서를 옮기는 키가 없다.
- 같은 테스트를 고르는 곳이 셋이다. 띠의 테스트 채널, 테스트 기록 표, 사고 기록의 경로 버튼이다.
  셋은 같은 상태를 바꾸지만 한곳으로 줄일지 정하지 않았다.
- 맨 위의 공용 "작업 상세" 제목과 그 아래 머리줄이 같은 정보를 두 번 보인다.

**다른 화면**

- 대시보드, 체인 구성, 모니터링, 기록, 노드, 테스트, 설정 화면은 색, 글꼴, 괘선만 바뀌었다. 배치는 장부
  형식이 아니다.
- 기록 상세(`HistoryPanel`)는 아직 옛 실행 타임라인(`RunTimeline`)과 `FailureMetrics`를 쓴다. 작업 상세와 같은
  실패를 다른 모양으로 보이므로, 기록계 띠로 맞출지 정해야 한다.

**품질과 도구**

- 글꼴은 시스템 글꼴을 쓴다. Avenir Next가 없는 환경(대부분의 Linux, Windows)에서는 대체 글꼴로 보인다.
  웹 글꼴 파일을 넣을지 정하지 않았다.
- critique 점수는 #461 지적을 고치기 전 28/40이다. 고친 뒤 다시 매기지 않았다. impeccable 마무리 검토
  agent는 돌리지 않았다. impeccable은 bun이 없어 제대로 설치되지 않은 상태였고, 사용자가 따로 고치는 중이다.
- #460 화면 확인 중 본 Svelte `derived_inert` 콘솔 경고를 #461 뒤에 다시 확인하지 않았다.
- 작업 중 web 디렉터리의 `node_modules`가 사라진 것은 사용자가 디스크 공간을 확보하려고 지운 것이다.
  `npm ci`로 다시 설치하면 된다.
- 시안 파일(web 디렉터리 아래 `.impeccable` 폴더)은 커밋하지 않고 작업 사본에만 있다.

## 6. 새로 생긴 계약

10-23 문서 4절의 계약에 아래를 더한다.

- `data-testid`: 원인 구역의 로그는 `cause-logs`, 단계 실패의 로그는 `phase-logs`다. 테스트 기록에서 펼친 줄은
  `run-cause`이고 `data-test`에 테스트 이름을 담는다. 사고 기록의 작업 정보에 `job-state`가 있다.
- 주소: 작업 상세는 `?test=`와 `?node=`로 고른 테스트와 로그 노드를 연다.
- 수집 공백: `recorder.mjs`의 `valueAt`은 기록된 null 표본이나 표본 간격 두 배를 넘는 거리에서 값이 없다고
  읽는다. 공백 안에서 직전 값을 보이지 않는다는 10-23 문서 5절의 교훈을 코드로 굳힌 것이다.
- 색: 컴포넌트에 색 값을 적지 않는 규칙(`design_tokens.test.mjs`)은 그대로다. 밝은 판과 어두운 판의 값은 모두
  `web/src/theme.css`에 있다.

## 7. 남은 작업 순서

2026-10-25 사용자 결정으로 첫 단계(Web UI 리팩토링)의 진행 방식이 바뀌었다. 화면을 먼저 고치지 않고, 쓸 수
있고 수집할 수 있는 데이터를 조사해 구조체와 타입, 수집과 갱신 구조를 정한 뒤 그 위에서 화면을 만든다.
조사 결과와 단계, 결정할 것은 [Web 데이터 모델 계획](web-data-model-plan.md)에 있다.

### 7-1. 데이터 모델 (다음에 바로 할 일)

[Web 데이터 모델 계획](web-data-model-plan.md) 3-1부터 3-6까지다. 데이터 인벤토리, 실제 표본 수집, 도메인 모델,
계약의 단일 출처, 수집과 전달 구조, 설정 입력 모델 순서다. 그 문서 6절에 사용자가 정한 방식(Go 구조체 원본, JSDoc 타입 검사, SSE 하나, 실패 증거는 비밀 검사 뒤 노출)을 따른다.

### 7-2. 그 위의 화면 작업

데이터 모델이 정해진 뒤에 한다. 사용자 영향이 큰 순서로 적는다.

1. **체인 구성 폼 정리.** 10-23 문서 2-1의 1번이다. 데이터 모델 계획 3-6에서 배포 계약에 제목과 설명이 붙으면
   라벨 문제가 함께 풀린다. 큰 흐름 변경이므로 `/impeccable shape`로 먼저 설계한다.
2. **다른 화면을 장부 형식으로 맞추기.** 대시보드, 모니터링, 기록 상세가 먼저다. 기록 상세는 작업 상세의
   기록계 띠를 다시 쓸 수 있는지부터 본다.
3. **어긋난 상태 표시.** 3절 표의 3번 묶음이다.
4. **주소로 가리키기의 나머지.** 기록 상세, 커서 시각, 대시보드 실행 ID 링크다.
5. **작은 것.** 화면 안 취소와 폐기 확인, 필터 칩 44px, 실행 중 경과 시간, 단계 구간 채널, 다음 오류 키,
   중복 제목.

**끝나는 조건.** `web/CLAUDE.md`의 "끝내기 전에"를 모두 지난다. 화면을 실제 표본 데이터로 데스크톱 폭과 좁은 폭,
밝은 판과 어두운 판에서 보고, critique를 다시 돌려 28/40과 비교한다. SPA를 다시 빌드해 함께 커밋한다.

**시작 전에 받을 결정.**
- 묶음을 PR 하나로 할지, 체인 구성 폼만 따로 뺄지.
- 기록 상세를 기록계 띠로 바꿀지.
- 같은 테스트를 고르는 세 곳을 줄일지.
- 웹 글꼴 파일을 넣을지. 넣으면 저장소와 SPA 크기가 늘고, 글꼴 라이선스를 확인해야 한다.
