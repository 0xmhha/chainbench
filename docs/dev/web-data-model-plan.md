# Web 데이터 모델 계획: 화면보다 데이터를 먼저 정한다

> **[측정] 2026-10-25.** 기준 커밋: main `0a18987c`. 코드와 기록을 읽어 조사한 결과이고, 아직 아무것도
> 구현하지 않았다. 사용자가 정한 것은 6절에 있다.

## 0. 왜 이 문서를 쓰는가

PR #461로 화면의 시각 기초(기관 일지 테마)는 잡혔다. 2026-10-25 사용자는 다음 단계를 화면이 아니라
데이터부터 하기로 정했다. 어떤 데이터를 쓸 수 있고 수집할 수 있는지 먼저 조사하고, 그 데이터를 담을
구조체와 타입, 백그라운드 수집과 화면 갱신 구조를 정한 뒤에 화면을 만든다. 대상은 두 갈래다.

- 화면에 보일 **런타임 데이터**: 노드 상태, 지표, 로그, 작업, 테스트 결과.
- Web에서 chainbench로 노드를 띄울 때 쓰는 **설정 데이터**: 배포 문서, 체인 preset, 테스트 정의, 작업 인자.

백엔드 쪽에서 이 일을 부르는 이름은 몇 가지가 겹친다. 이 문서에서는 이렇게 쓴다.

- **데이터 인벤토리(데이터 사전)**: 어떤 데이터가 어디서 언제 만들어지고, 단위와 타입이 무엇이며, 비어 있을
  수 있는지를 한 곳에 적은 목록이다.
- **도메인 모델(데이터 모델)**: 그 데이터를 담는 구조체와 관계, 상태 이름을 정한 것이다.
- **API 계약**: 서버와 화면이 주고받는 모양을 한 출처에서 정하고 양쪽이 그것을 따르게 하는 것이다.
  계약을 먼저 정하고 구현하는 방식을 contract-first 또는 schema-first라고 부른다.
- **읽기 모델(read model, projection)**: 원본 기록을 화면이 바로 쓸 수 있는 모양으로 서버가 미리 가공한 것이다.

## 1. 무엇을 보고 판단했나

세 갈래로 나눠 읽었다.

1. 엔진과 대시보드가 디스크에 쓰는 기록, 백그라운드에서 수집하는 값, 작업 상태 기계, API가 데이터를 읽는 길.
2. 화면이 쓰는 설정 입력: 배포 계약, 체인 preset 계약, DSL, 설정과 자격증명, 작업을 제출하는 길.
3. 지금까지 남은 실제 기록: 저장소의 증거 JSON, Web 인수 기록, 작업 사본의 `chainbench-out/`(gitignore 대상).

## 2. 무엇이 문제인가

### 2-1. 같은 개념이 여러 모양으로 있다

- 블록 높이와 피어 수가 네 군데에 다른 모양으로 있다. Web 모니터 표본(5초), 엔진 수집기의 `chainstate.jsonl`(2초),
  `health.NodeInfo`(snake_case), `app.NodeReadings`(camelCase)다. 블록 높이는 이름도 둘이다. RPC로 읽은
  `block_height`와 metrics 끝점에서 읽은 `chain_head_block`이다.
- 실행 상태를 나타내는 어휘가 다섯이다. `RunStatus`, `TestStatus`, `StepState`, `WebJob.state`, `WebRun.state`다.
- 필드 이름 표기가 섞여 있다. 엔진 기록(`steps.json`, `assert.json`, 프로세스 장부)은 json 태그가 없어 PascalCase로
  쓰이고(`internal/core/session/record.go`), Web 응답은 camelCase, `env.json`의 노드 주소는 snake_case(`rpc_url`)다.

### 2-2. 계약이 한 곳에 있지 않다

- OpenAPI 명세(`docs/dev/web-ui.openapi.yaml`, 4천 줄)는 아무것도 생성하지 않는다. 테스트는 명세가 파싱되는지와
  경로가 등록된 라우트와 맞는지만 본다. 스키마가 Go 구조체나 화면 코드와 맞는지는 아무도 확인하지 않는다.
- 실제로 어긋난 곳이 있다. 명세의 `PlanInput.arguments`는 아무 필드나 받는다고 적혀 있지만, 서버는 모르는 필드를
  거절한다(`internal/app/web_chain_engine.go`의 `DisallowUnknownFields`).
- 화면은 타입이 없는 JavaScript다. JSDoc도, 타입 검사 설정도 없다. API를 부르는 fetch 감싸개가 공용 모듈 말고도
  열 곳 넘게 따로 있다.
- 작업 상태 목록, 역할 이름(`administrator`와 `admin`), 새 문서의 기본값이 Go와 화면에 손으로 두 번 적혀 있다.

### 2-3. 화면이 엔진의 디스크 형식을 직접 읽는다

실행 타임라인은 기록 요약에 담긴 테스트별 원본 파일(`assert.json`, `steps.json` 등)을 브라우저에서 파싱해 테스트 줄,
실패한 단언, 스텝 오류, 관련 노드를 만든다(`web/src/run-timeline.mjs`). 그래서 엔진이 기록 형식을 바꾸면 화면이
조용히 깨진다. 노드 집계, 주의 작업, 최근 표본, 커서 사이의 최댓값도 화면에서 계산한다.

### 2-4. 수집과 전달의 길이 여럿이다

- 작업 변화는 SSE(`/api/v1/events`)로 오지만, 지표와 로그는 REST를 5초마다 다시 부른다. 설계 문서가 계획한
  지표 SSE는 구현되지 않았다.
- 옛 길이 남아 있다. `/events`는 엔진 버스 이벤트를, `/api/runs`는 아무도 기록하지 않아 늘 빈 목록을 돌려준다.
- 수집 공백의 이유는 구조가 있지만(`node`, `source`, `reason`), 읽을 때 문자열 하나로 합쳐진다
  (`internal/app/web_monitor_read.go`). 화면은 그 문자열을 다시 쪼개야 한다.

### 2-5. 있는데 화면에 오지 않는 데이터가 있다

- 테스트가 실패했을 때 남기는 증거(`observations/`의 health, 프로세스 목록, 노드 로그)는 기록 수집 허용 목록에 없다.
- `chainstate.jsonl`(BP 참여, 포크 여부)은 옛 경로로만 읽힌다.
- 엔진 생명주기 상태와 전이 기록, 체인 기록의 단계 정보는 Web API로 나오지 않는다.
- Web의 실행 기록에는 엔진 세션의 끝난 시각이 없다. 세션 기록 자체에 그 필드가 없기 때문이다.

### 2-6. 설정 입력이 엔진이 받는 것보다 좁고, 오류 위치를 잃는다

- 배포 계약은 Go 구조체에서 반사로 만든다. 그래서 설명, 형식, 패턴이 없고, 열거값과 범위도 몇 필드에만 있다.
- 서버 검증 오류는 `/content` 한 곳만 가리키고, 화면은 그 경로마저 버린다(`web/src/DeploymentEditor.svelte`).
- CLI의 `chain up`이 받는 `--en`, `--pn`, `--topology`, `--peering`, `--bootnode`, `--docker` 같은 인자를 Web은
  표현하지 못한다. preset이 없으면 `--bp` 하나만 넘긴다.

### 2-7. 실제 표본이 거의 없다

예전 Web 인수 실행 루트(`/private/tmp/cbui`)는 지금 이 기기에 없다. 남은 실제 기록은 작업 사본의
`chainbench-out/`뿐이고, 그것도 다른 clone에는 없다. 그 안에서도 다음 데이터는 실제 표본이 하나도 없다.

- 내용이 있는 노드 로그 줄.
- `startedAt`, `finishedAt`이 있는 새 형식 `status.json`. 남은 42개는 모두 옛 형식이다.
- 실패한 세션. 남은 세션은 모두 통과했다.
- 긴 지표 계열. 남은 계열은 노드마다 표본이 두 개쯤이다.
- 기록과 비교 API 응답, SSE 페이로드, 원격(SSH) 지표 계열.

#461까지의 화면 확인은 모두 손으로 만든 mock 데이터로 했다. 그래서 화면이 실제 데이터 모양과 맞는지는 아직 모른다.

## 3. 제안하는 작업 순서

각 단계는 앞 단계의 결과를 입력으로 쓴다. 단계마다 끝나는 조건을 적는다.

### 3-1. 데이터 인벤토리를 만든다

화면에 보이거나 설정으로 들어가는 데이터마다 한 줄씩 적는다. 적을 칸은 이름, 만드는 곳(파일과 함수), 만드는
시점과 주기, 저장 위치, 단위와 타입, 비어 있을 수 있는지, 큰 정수의 표기, 공백이 생기는 이유, 쓰는 화면이다.
1절의 조사 결과가 초안이 된다.

**끝나는 조건.** 지금 화면이 쓰는 모든 API 응답 필드가 인벤토리의 한 줄로 거슬러 올라간다. 2-5절의 "있는데
안 오는 데이터"마다 노출할지 말지를 적는다.

**현재 상태 (2026-10-25).** 인벤토리는 [web-data-inventory.md](web-data-inventory.md)에 있다. 필드 추적은 채웠고,
노출 여부는 후보만 모은 채 3-3단계에서 정한다. 조사 중에 찾은 결함 셋은 #466에서 고쳤다.

### 3-2. 실제 표본을 다시 모은다

로컬 체인 하나(예: stablenet 4노드)를 띄우고, 일부러 실패하는 테스트를 포함한 작업을 Web으로 돌린 뒤 30분쯤
수집한다. 그 결과로 로그 줄, 실패 세션, 새 형식 `status.json`, 긴 지표 계열, SSE 페이로드를 얻는다. 비밀을 지운
뒤 테스트 고정 데이터로 저장소에 넣고, 화면 확인용 mock은 이 표본에서 만든다.

**현재 상태 (2026-10-25).** 첫 30분 수집을 마쳤고, 확인한 사실은 [인벤토리](web-data-inventory.md)의 "실제 표본으로
확인한 것"에 적었다. 표본에서 경로와 식별 값을 지워 `tests/webui/fixtures/stablenet-sample/`에 넣었다. `0001-01-01` 시각은 실행 중인 단계에서만 나온다는 것을 3-3단계에서 코드와 직렬화 실험으로 확인했다. 화면 확인용 mock은 3-4단계 끝에 모델 모양으로 만들고, 원격 지표 표본은 3-5단계에서 SSH 고정 환경으로 모은다.

**끝나는 조건.** 2-7절에 적은 "표본 없음" 항목이 원격 지표를 빼고 모두 채워진다. 원격 지표는 SSH 고정 환경이
필요하므로 따로 정한다.

### 3-3. Web 도메인 모델을 정한다

화면이 쓰는 개념을 하나씩 정한다. 네트워크, 노드, 노드 관측, 지표 계열과 표본과 공백, 로그 줄, 작업과 단계,
실행과 테스트 결과와 단언과 스텝, 이벤트다. 정할 것은 다음과 같다.

- 상태 어휘를 하나로 맞추고, 엔진의 다섯 어휘가 그것에 어떻게 대응하는지 표로 둔다.
- 블록 높이처럼 출처가 둘인 값은 하나를 정본으로 고르고, 다른 하나는 보조 출처로 표시한다.
- 공백 이유는 문자열이 아니라 `node`, `source`, `reason` 구조로 보낸다.
- 큰 정수는 10진 문자열로 보낸다. 지금 엔진이 하는 방식을 계약으로 굳히는 것이다.
- 엔진의 디스크 형식(PascalCase)은 바꾸지 않는다. 대시보드가 읽어서 Web 모델로 옮긴다. 새 진입점은 엔진을
  다시 구현하지 않고 감싸기만 한다는 기존 원칙을 따른다.

**끝나는 조건.** 개념마다 필드, 타입, 필수 여부, 출처가 정해져 있고, 3-2의 실제 표본이 모두 그 모델로 옮겨진다.

**현재 상태 (2026-10-26).** [도메인 모델](web-domain-model.md)에 관측, 작업, 실행 기록의 개념과 노출 결정을 적었다.
`tests/webui/web-domain-model.test.mjs`가 표본 전부를 모델로 옮겨 본다. 설정 입력의 모델은 3-6단계로 넘겼다.

### 3-4. 계약의 단일 출처를 정하고 검사로 묶는다

Go 응답 구조체를 원본으로 삼고(6절의 1), OpenAPI와 어긋나면 실패하는 테스트로 묶는다. 화면 타입은 JSDoc으로 적고
svelte-check로 검사한다(6절의 2). 화면에는 응답을 받는 공용 클라이언트 하나와 응답 모양을
확인하는 해독 함수를 둔다. 모양이 틀린 응답은 화면을 깨뜨리지 않고 "데이터 형식 오류"로 보인다.

**끝나는 조건.** API 응답 필드를 하나 지우거나 이름을 바꾸면 테스트가 실패한다. 화면의 fetch 감싸개가 공용
클라이언트 하나로 모인다.

**현재 상태 (2026-10-26).** `internal/app/web_openapi_contract_test.go`가 Go 응답 구조체와 OpenAPI 스키마를 비교한다.
필드 이름, 늘 나가는 필드와 필수 목록, JSON 종류가 다르면 실패한다. 처음에는 노드, 네트워크, 단계, 작업,
커버리지, 지표, 로그, 실행 기록과 그 쪽, 문서, 작업 공간을 묶었고, 뒤에 사용자, 세션, 자격 증명, 자산, 감사 기록, 계획, 자원 충돌, 비교, 어휘, 체인 표면, 문서 검증과 가져오기를 더했다. 묶지 않은 것은 `internal/dashboard`가 맵이나 익명 구조체로 만드는 응답(스냅숏, 공통 쪽, 자격 증명 사용처, 오류 본문)과 입력 스키마다. 처음 돌렸을 때 나온 어긋남은 모두 고쳤다. 실행 중인
단계의 끝 시각은 이제 빠지고, OpenAPI에는 구현되지 않은 노드 `ports`가 빠지고 `caseRefs`와 재확인 결과의 모양이
들어갔다. 누락 구간은 `scope`, `nodeId`, `source`, `code`, `metric`, `runId` 필드로도 나가고, 멈춘 노드의 구간은 `node_stopped` 누락으로 기록한다. 노드는 `ref`를, 지표 계열은 `metric`과 `canonical`을, 작업은 `terminal`과 `needsCheck`를 함께 보낸다. 화면은 아직 옛 필드를 읽는다. 실행 기록 상세는 엔진 결과 파일을 읽은 `tests`(단언, 스텝, 후속 동작, 산출물)를 보내고, 단언의 기대값과 실제값과 스텝의 nonce는 10진 문자열이다. `missingDimensions`는 상세를 읽을 때 다시 계산한다.

`/networks`와 `/snapshot`의 노드 상태를 실제 관측으로 바꾸는 일은 3-5단계로 옮겼다(2026-10-27 사용자 승인). 목록을 읽을 때마다 프로세스를 관측하면 SSH 대상에서 느려지므로, 수집기가 관측한 결과를 시각과 함께 싣는 구조가 먼저 필요하다. 그때까지 두 응답의 노드 상태는 `unknown`이고 실제 상태는 `/observations`에만 있다. 남은 일은 나머지 응답을 도메인 모델 모양으로 바꾸는 것, 나머지 스키마를 묶는 것, 화면의 공용 클라이언트와
해독 함수, 그리고 표본으로 만드는 화면 확인용 mock이다.

### 3-5. 수집과 전달 구조를 정한다

3-4단계에서 옮겨 온 일: 수집기가 관측한 노드 상태를 `/networks`, `/snapshot`, 스트림에 시각과 함께 싣는다.

- 실행 타임라인처럼 화면이 원본 파일을 파싱하던 계산을 서버의 읽기 모델로 옮긴다.
- 지표, 로그, 노드 상태 변화를 작업용 SSE 스트림에 함께 싣는다(6절의 3).
- 옛 `/events`와 `/api/runs`를 지운다.
- 2-5절에서 노출하기로 한 데이터의 API를 만든다.

**끝나는 조건.** 3-2의 실제 표본으로 대시보드를 띄워, 수집이 멈췄다 다시 시작되거나 서버가 다시 뜨는 경우에도
화면이 공백을 공백으로 보이고 오류 없이 따라온다.

### 3-6. 설정 입력 모델을 정한다

- 배포 계약에 제목, 설명, 형식을 더한다. 스키마의 제목을 화면 라벨로 쓰면 체인 구성 폼 정리(인계 문서의 1번)가
  저절로 쉬워진다.
- 검증 오류가 필드 위치를 담게 하고, 화면이 그 위치에 오류를 보인다.
- 작업마다 받는 인자를 스키마로 정하고, OpenAPI의 "아무 필드나 받음"을 없앤다. 노출하는 인자는 구현이 실제로
  읽는 것만 고른다. 모르는 인자는 편집기와 검증이 모두 거절한다는 기존 결정을 따른다.
- CLI가 받는데 Web이 못 받는 인자 가운데 preset으로 표현할 수 없는 것을 골라 열지 묻는다(6절의 4).

**끝나는 조건.** Web에서 보낸 설정이 어떤 CLI 인자가 되는지 작업마다 표로 확인할 수 있고, 그 표가 테스트로 묶인다.

### 3-7. 그 위에서 화면을 만든다

인계 문서에 남은 화면 작업(체인 구성 폼, 다른 화면의 장부 형식, 상태 표시, 주소, 작은 것)은 이 모델 위에서 한다.
그래야 화면마다 데이터를 다시 해석하는 일이 없어진다.

## 4. 단점과 위험

- **화면 개선이 늦어진다.** 3-1부터 3-6까지는 사용자가 보는 변화가 거의 없다.
- **표본을 모으려면 실제 체인이 필요하다.** 맞는 바이너리, 포트, 디스크 2 GiB 이상이 있어야 하고, 실행 중에는 같은
  포트를 쓰는 다른 증명과 겹치면 안 된다.
- **계약 생성 도구를 들이면 의존성이 는다.** 지금 화면 의존성은 vite와 svelte 둘뿐이다. 코드 생성이나 타입 검사
  도구를 넣으면 빌드 단계와 갱신 부담이 생긴다.
- **엔진 기록 형식은 그대로 둔다.** PascalCase를 고치면 옛 기록을 읽는 코드가 깨지므로, 번역 비용을 대시보드가 진다.
- **WEB 인수 계약을 지켜야 한다.** 화면 구조나 API를 바꿀 때 브라우저 인수 스크립트가 기대는 `data-testid`와
  로그 API 계약(10-23 인계 4절, 10-25 인계 6절)을 깨지 않아야 한다.

## 5. 인수 확인 시점

WEB-01~14 전체 capture는 Web 리뉴얼을 마치고 주요 기능 몇 개가 실제로 동작하는 것을 확인한 뒤 한 번만 한다

## 6. 정한 것

2026-10-25 사용자가 아래처럼 정했다. 4번과 6번은 지금 정할 근거가 부족해 기준만 정했다.

1. **계약의 원본은 Go 응답 구조체다.** OpenAPI는 손으로 고치되, Go 구조체의 json 필드와 OpenAPI 스키마가 다르면
   실패하는 테스트를 더한다. 새 생성 도구는 들이지 않는다. 배포 계약이 이미 Go 구조체에서 만들어지는 방식과 같다.
2. **화면 타입은 JSDoc과 타입 검사로 둔다.** 파일은 `.js`와 `.svelte` 그대로 두고 주석으로 타입을 적은 뒤,
   빌드 때 svelte-check로 검사한다. 개발 의존성 svelte-check와 typescript가 늘지만 화면 번들에는 들어가지 않는다.
   API 경계에는 응답 모양을 확인하는 해독 함수를 함께 둔다.
3. **실시간 전달은 SSE 하나로 모은다.** 작업용으로 이미 있는 `/api/v1/events` 스트림에 지표, 로그, 노드 상태 변화를
   싣는다. 끊기면 스냅숏으로 다시 맞추는 기존 구조를 그대로 쓴다. 로그는 보낼 양을 제한한다.
4. **Web에서 열 CLI 인자는 인벤토리 뒤에 정한다.** 노드 구성(역할별 수, 부트노드, 동기화 방식)은 체인 preset
   계약에 이미 있으므로, preset으로 표현할 수 없는 인자만 3-1에서 골라 3-6에서 다시 묻는다. 구현이 실제로 읽는
   인자만 연다는 기존 원칙을 따른다.
5. **실패 증거는 비밀 검사를 거친 뒤 Web 기록에 넣는다.** 프로세스 명령줄과 로그에 키나 비밀번호가 섞일 수 있는
   항목을 검사해 가린다. 그 검사는 테스트로 묶는다.
6. **표본은 로컬 stablenet 4노드로 모은다.** 남은 실제 세션이 모두 stablenet이기 때문이다. 바이너리는 바이너리
   선택 파일이 가리키는 것을 쓰고, 띄우기 전에 포트와 디스크를 확인한다.
